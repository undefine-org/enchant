& Split.

Hayleigh, the familiar starting point is a view function. The interesting next questions are who owns its inputs, who performs an effect, and which work can happen in the browser.

01 / Three names, one conversation

Loom is the presentation vocabulary: tokens, layout and components that return a UI tree. Live connects a view to changing database values and sends DOM patches. Split explores placing the view and optimistic predictions in the browser while the BEAM owns shared decisions.

Implementation boundary. Live is the integrated server-rendered application path. The explicit split/defapp snapshot-and-intent model is a separate prototype. The diagrams below explain that model; automatic splitting of ordinary live.app screens remains a design direction. The current actor-demo builder does not regenerate the checked-in Split demo bundles.

02 / Start with the part that feels familiar

Lustre's view(model) → Element(message) and Beam Lisp's view have the same useful starting shape: inputs in, a description of the screen out. Lustre's full application returns a model and an Effect(message) from update; its runtime performs the effect. See Lustre's managed-effects guide.

In Beam Lisp, a Hiccup tree is an ordinary nested value: 

[:button {:on-click [:intent :tick {:id 3 :got true}]}
 "Got it"]

The tag, attributes, children and event description are all data. A component is a function returning more of that data. Loom adds a coherent vocabulary for spacing, colour, layout and accessible controls: 

(ns hayleigh.frontend
  (:require [loom.box :as b] [loom.ui :as ui]))

(defn task-card [task]
  (b/col {:gap :3 :pad :5 :border true :radius :lg}
    (ui/heading {} (:name task))
    (ui/button {:variant :primary
                :on-click [:intent :tick
                           {:id (:id task) :got true}]}
      "Got it")))

Read this as: a column, a heading, a button, and an event to emit. Loom turns layout properties into CSS classes and returns Hiccup. It collects the generated stylesheet within the render context. The component describes the action; Live interprets it.

03 / The model has owners

For a Live view, the useful model is a composition of shared database values, a private session database value, and locals. Ownership tells you where a change belongs.

Shared facts are things other people can observe: tasks, votes, purchases. Session facts hold richer private state that benefits from queries and history. Locals hold small UI choices such as a filter or selected row. Persistence depends on the connection's store; a shared in-memory connection is still in memory.

At the socket layer, the view signature is: 

view(shared-db, session-db, locals) → Hiccup

At the application layer, a screen receives a context map containing named worlds, route parameters and viewer information. The app supplies the already-guarded worlds for that viewer. This lets the screen work with the data it is allowed to see.

The database arguments are values, so a view can query a fixed snapshot and return a tree you can inspect directly. The connection and its writes belong to the runtime and registered performers.

04 / A filter and a fact take different paths

A filter changes this person's view of the world. Ticking a shared task asks to change the world other people see. Both gestures are event data, with different owners: 

;; A private UI choice: copy the input value into this session's locals.
[:input {:value (:filter locals)
         :on-input [:assign :filter [:from :value]]}]

;; A shared change: ask the registered performer to tick task 3.
[:button {:on-click [:intent :tick {:id 3 :got true}]}
 "Got it"]

An :assign updates locals and schedules this viewer's projection. An :intent goes through authorization and a registered performer. The Live performer receives (connection, payload, principal) and returns transaction data, nil for a no-op, or {:refused reason}. The runtime submits returned transaction data to the selected connection. A server registration can also target the private session connection.

A shared commit notifies observing sessions. Each session projects its own view, diffs it against its previous tree, and sends patches. Stable keys let rows retain identity across inserts and moves. The browser applies those operations to the DOM.

05 / What “effect” means here

The application-facing idea is simple: describe an operation as data; let the owner interpret it. A button returns an event description. A performer returns transaction data. The runtime owns the socket, the transaction, the subscriptions and the DOM boundary.

This is a useful bridge to Lustre's managed effects. Beam Lisp's Live API expresses its UI actions with :assign, :intent and :navigate terms; it does not expose a general Effect(message) return value from one universal update function. Registered performers are ordinary Beam Lisp functions and may themselves do effectful work.

There is also a compiler meaning of effect: the analyzer records which resources code reads, writes, sends to, receives from or spawns. Effects flow through calls, including work deferred inside function values and lazy sequences. Unknown code does not earn a purity proof.

system.place admits local computation when it has an empty immediate footprint, an empty latent footprint and proven termination. Target compilation must also support the operations involved. This is a conservative placement check, not an automatic deployment system for every Live screen.

Loom's theme and stylesheet collection is render bookkeeping. Calling a screen a pure projection describes its domain model; it does not promise that every styling helper passes the compiler's stricter empty-footprint check.

06 / Split gives the browser a local loop

The explicit Split prototype makes the boundary visible in one declaration. It names the client view and event reducer, the server's initial state, the public snapshot shape, and each permitted intent's roles.

The browser's event reducer has a familiar shape: 

(defn on-event [local event]
  (case (first event)
    :draft {:local (assoc local :draft (nth event 1))}
    :tick  {:local local
            :intent [:tick-item {:id (nth event 1)
                                 :got (nth event 2)}]}
    {:local local}))

Typing returns a new local model. Ticking also returns an intent for the runtime to queue. These are Split's own event terms, declared by its :on function; Live's [:intent …] vocabulary belongs to its socket interpreter.

The declaration connects ordinary functions to responsibilities:

Role Runs where Responsibility
:view Browser (shown-board, local, sync) → Hiccup
:on Browser (local, event) → local + optional intent
:check Both Check public rules; return nil or a reason.
:predict Browser Calculate the board the user expects.
:allow Server Check the authenticated person's permission.
:guard Server Check rules needing private state.
:apply Server Calculate the next authoritative state.

The wire shapes say what may cross the boundary. The server projects its private state onto the public snapshot shape. Both halves carry a digest of the data contract; a mismatch is refused. That digest covers shapes and parameters, so matching digests alone do not establish identical application logic.

The server rechecks the proposal's parameters, revision, public rules and permissions. A prediction can improve the experience; it grants no write authority.

07 / Optimism is a calculation

The Split client owns three distinct inputs: its last confirmed board, its local UI state, and its pending intent queue. Its view receives a board derived by folding predictions over the confirmed board, plus local state and synchronization information.

Acceptance removes the resolved intent and adopts the server's board. Refusal removes its prediction; the screen derives again from confirmed data and any remaining predictions. If another tab committed first, a stale-revision response supplies a newer board and the client rechecks and retries within its retry bound.

The view can see pending operations, connection status and refusal information, so it can show “saving”, “waiting” or a reason. In this prototype, the app authors that feedback. The queue can retain work across a connection gap while the client is alive; persistence across a page reload is a separate concern.

For delivery retries, the client keeps the proposal's nonce. The authority remembers a bounded window of committed nonces and answers duplicates without applying them again. A configured commit hook can persist before acknowledgement.

08 / The vocabulary bridge

Starting from Lustre The corresponding Beam Lisp idea
A model Live's shared/session values + locals; Split's board/local/sync.
view(model) A function returning Hiccup, composed with Loom.
A message An event term containing an operation and payload.
update(model, message) Live's event interpreter and performers; Split's :on reducer.
A managed effect An operation description interpreted by its runtime owner.
External results Commits, snapshots, acknowledgements and refusals feed projection.

The design question I would bring to you is: how much of the local update loop can we move next to the person, while keeping shared decisions in one authoritative place? Loom supplies the screen vocabulary. Live supplies projection over changing facts. Split makes local prediction and shared authority explicit.
