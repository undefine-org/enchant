Measured on OTP 29 / Elixir 1.20.2 in /home/user/code/undefine/beam-lisp.

BeamLisp.eval/1 compiles each call into a fresh module (Elixir.BeamLisp.Eval.M<n>):
- eval "(+ 1 2)"                 6.55 ms/op
- eval "(defn q [x] …) (q 5)"   32.66 ms/op
- Reader.read_string (no compile) 0.019 ms/op   ← 340x cheaper

Leak profile over 500 evals: modules 800 -> 1807, atoms 27275 -> 28294.
Purging Elixir.BeamLisp.Eval.* reclaims modules (395 -> 1) but atoms are
monotonic (27307 -> 27928 -> 28536 across two purged cycles). Atom exhaustion
is a whole-VM abort, not a catchable exception (docs/trust-boundary.md).

=> Never route a hot/untrusted data path (wire events, cassettes, tool args)
through BeamLisp.eval. Reader.read_string returns reader FORMS ({:map, [...]}),
not data, so there is currently no data-reader path at all. Building one
(tagged binaries, bounded intern sites, String.to_existing_atom first) is
specified in docs/trust-boundary.md but not implemented.

Other measured facts:
- pr-str 200-node tree: 866 us, 8326 bytes. term_to_binary same tree: 39 us,
  8735 bytes (22x faster).
- Agent-backed atom deref: 4.5 us/op. persistent_term get: 0.64 us/op.
- Named-process state (Agent with {:name, :x}) survives a full module re-eval,
  same pid — a stronger `defonce` than Clojure's.
- Distribution works: `elixir --sname X -S mix beam_lisp.run` => Node.alive?() true.
