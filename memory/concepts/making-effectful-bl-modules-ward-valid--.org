A test that mutates GLOBAL state can be made ward-isolation-valid by injecting the RESOURCE the effect writes to — the BEAM way to mock (don't stub functions; parameterize the sink).

CASE (PLAN-058 W1): reload/commit wrote to the literal env :global (env/with-env :global in apply-bundle!). Under a ward env/isolated fork, the test read the fork but reload wrote :global. The break was subtle and asymmetric: Env.callers_of / ns_defs / namespaces are CHAIN-AWARE (read through fork→:global), but Env.own_names is EXACT-ENV (key({ns,$1}) = current env only, env.ex:788). So the fork's own_names returned [] while callers_of found the caller — removed-names (which uses own_names) saw nothing removed → cross-ns removal check never fired → :applied instead of :held. This is why a reconcile test passed under `mix beam_lisp.test` (run_suite_serial evals a single file in :global WITHOUT forking, test_rt.ex:254) but false-failed under ward.

FIX: reload gains a per-process commit target (process dict, key :reload/commit-target, default :global) with commit-target/with-target; apply-bundle! uses (commit-target) instead of literal :global. ward binds the target to each file's fork (reload/with-target (env/current)). Now commit writes where the test reads → coherence (own_names) and the write agree → correct verdict, AND the edit lands in the fork (destroyed on exit, zero :global leak). Verified: whole reload suite green via run-sandboxed, 0 leak, mix path unchanged (default :global).

GENERAL PATTERN: when a bl module has a hardcoded global side-effect target that breaks under env/isolated, make the target a per-process dynamic binding (erlang/put+erlang/get, restored in a try/finally) defaulting to the global. The isolating runner binds it to its fork. Strictly better than making the exact-env query chain-aware (which would change the module's semantics everywhere).

TWO BEAM GOTCHAS from the same plan:
1. A message from an Erlang lib arrives as a TUPLE, which is NOT `sequential?` in bl (our own [:tag …] vectors ARE). A cond guard on (sequential? msg) silently drops tuple messages (e.g. FileSystem's {:file_event fs payload}). Normalize with `first` (reads head of tuple OR vector); nth/second also work on both.
2. BEAM-native progress = the worker emits a :start event before working and a :done after, over the same message channel — no polling, no timer. ward's run-file-eventful fires {:phase :file-start} then {:phase :file-done}; a live dashboard renders a 'running' tile on start, resolves it on done. Debounce a burst of events with a per-process generation counter + :erlang.send_after (only the latest gen fires).
