Two tabs on one database go stale the moment either writes. The obvious
fix — broadcast the fresh view to everyone — produces working code and a
wrong system.

## Why sending the view is wrong

A view is a function of (data, WHO IS ASKING). The writer knows only its
own half.

Reel's board is role-scoped: the same task offers `[doing dropped]` to a
tech lead and `[dropped]` to a product lead, because
`reel.work/affordances` intersects legality with permission. If tab A's
write broadcasts tab A's board, tab B renders affordances computed for
the wrong person — offered an action it will then be refused for.

That is the failure a lifecycle-as-data design exists to prevent,
reintroduced through the notification path, and it only appears with two
tabs open AS DIFFERENT USERS. Which is to say: almost never in a test,
and immediately in real use.

## What IS true at the instant of a write

Exactly one thing: the data advanced from basis N to N+1.

Which rows changed, whose screen now differs, what any given client
should display — all DERIVED by the reader from its own question. None
of it is knowable to the writer.

∴ **the payload is a basis. A number.** Each subscriber re-runs the read
it already has, as itself.

## The second-order trap: where the identity lives

Getting the payload right is only half. The re-read runs on the SERVER,
in a `handle_info` — which cannot see a browser-local signal.

Reel's `@role` was page-local (written by `st/on :input`). A woken page
would have re-read with no role and quietly reset to the default lead: a
product lead who merely WATCHED a task appear would find themselves
holding tech's affordances, having touched nothing.

Fix: the identity must be a server-visible assign, because
`handle-info` is handed `current_assigns` exactly as `handle` is. Pin it
with a test that wakes a page holding a non-default role and asserts it
keeps its own answer.

## Broadcast adds no rendering path

The subscriber re-runs the SAME handler a manual refresh runs. That is
the point: a second way for a page to acquire state, parallel to the
first and able to disagree with it, is the thing to avoid. Broadcast
supplies a REASON to re-run, not a new way to render.

## Where the announce belongs

At the single write chokepoint (`reel.store/transact-as!`), not in the
handler that requested the write. A future writer that forgets to
announce is a page that silently goes stale — surfacing as "the board is
wrong sometimes", weeks later, in a tab nobody had open while testing.

And the DECISION cannot live in the host: `perform_intents` receives a
map of assigns for a refusal exactly as for a success, so it cannot tell
them apart. The domain can. Same split `do!` makes, running the other
way — the domain decides WHETHER, the host owns the AUTHORITY.

## Operational notes

- Subscribe on the CONNECTED mount only. Phoenix mounts twice per
  navigation; the disconnected pass runs in a request process that exits
  immediately, so subscribing there registers a dying pid and doubles
  every delivery until it goes.
- A missing PubSub must not raise. It is started in serve mode only, so
  `mix run --no-start` scripts have none — and losing a write because
  nobody could be notified about it is a spectacular trade.
- PubSub server name from config, never a literal: each app names its
  own (`SpellWeb.PubSub`, `Reel.PubSub`).
- Elixir atoms with `/` or `.` MUST be quoted in generated source:
  `{:spell/changed, _}` is a syntax error, `{:"spell/changed", _}` is
  not. Namespaced tags are the normal spelling for a cross-app message,
  so it is the first shape a real user hits.

## The test that can actually fail

TWO sockets. A single-socket test cannot fail for the reason the feature
exists — the bug IS the second page, the one that did not write and has
no reply coming. Verified live: tab A (product) and tab B (default) both
holding the same new task, offering `[dropped]` and `[doing dropped]`
respectively.
