Two non-obvious implementation facts from wave 26 (core gaps) in beam-lisp:

1. A transducer-returned reducing step (e.g. `(take n)`'s xform in RT.take_xform) must answer 0/1/2-arg calls as a `multi_fn` tag, NOT a plain Elixir closure — an Elixir closure is fixed-arity, and a 2-arg step call from beam-lisp's reduce blows up with "arity 1 called with 2 arguments". Build it with `multi_fn(%{0=>..,1=>..,2=>..})`.

2. `transduce`'s completion `(f ret)` delegates to the reducing fn's 1-arity. So the reducing fns used with transduce need a 1-arity completion passthrough: `conj` (`(conj coll)`→coll) and `conj!` (`(conj! t)`→t). The real completion is `persistent!` in `into`, so the 1-arity is a no-op. Both are Clojure-faithful (`conj` has a 1-arity identity).

Also: prelude ordering in priv/core.bl is strict — a def that compiles the `or` macro must come AFTER `or` is defined, else the macro value leaks into runtime and invoke has no `$macro` clause. Symptom: "no function clause matching in BeamLisp.RT.invoke/2" with a `$macro`-wrapped blfn.

rem vs mod: `:erlang.rem/2` exists as a BIF (unlike `div` assumptions) and matches Clojure's rem (sign of dividend). rem(-7,3)=-1, mod(-7,3)=2.
