Built 2026-08-15 (commits 81d3188, 227cac0). `PROVIDER=fake mix run --no-halt scripts/serve_live.exs` → http://127.0.0.1:4030. One BEAM node: machine, generated server half, page, endpoint, provider.

The insight that shaped it: a contract's handler bodies are already beam-lisp data (`set!`/`push!`/`ask!`/`ok`/`err`, `on-info` patterns for streaming). Every projection existed — page `@data` forms, contract.json sidecar, reply tags — EXCEPT the one that runs them. So: `spell.server` walks bodies with a CLOSED vocabulary (not eval — bodies can be model-proposed), and `spell.contract/elixir-module` emits the LiveView that delegates to it. spacetime_lv does the reverse (hand-write LV, derive contract.json); spell's direction means the two cannot disagree.

Transport: verse's `live` host carries all three seam directions over ONE LiveView channel (signal→reply, assign diffs via st-set, streams). No SSE, no http host, no second app — Phoenix is a library in beam-lisp's own supervision tree.

Defects that only appeared once bodies executed: `append` was undefined though the seed called it; `(on :send [text] …)` folded params into the body and lost the names (wire is positional — `fire :send @draft` sends a BARE STRING payload); the contract never joined the finished answer to @messages despite its comment saying so; `(st/each @fx …)` cannot work because a stream decodes to the LATEST variant, not a list; an `""` dispatch arm emits an empty pattern the grammar refuses (E0946).

Traps for next time: port 4000 was held by an unrelated project's Phoenix app, so an endpoint that never started looked like 404s from ours (Phoenix starts NO listener without an `http:` config key); Phoenix defaults to Cowboy, this repo has Bandit (`adapter: Bandit.PhoenixAdapter`); prebuilt client JS in deps exposes `window.Phoenix.Socket` and `window.LiveView.LiveSocket` (NOT `window.LiveSocket`); `Compiler.eval_string` runs in the CALLING process, which is how `(erlang/self)` reaches the LiveView pid for streamed tokens.
