** ITEM binary_to_term with [:safe] makes an unknown atom read as "no data at all"

Measured 2026-09-16 in beam-lisp, while a prototype added a key to the port-claim term.

`BeamLisp.Daemon.Ports.read_claim/1` decodes claim files with:

    :erlang.binary_to_term(bin, [:safe])

`[:safe]` REFUSES a binary that contains atoms the reading VM does not already have. So a claim carrying one unfamiliar atom is not "a claim with an extra field" — it is **not a claim at all**, and the registry silently reads as EMPTY. No error, no warning, indistinguishable from "no session is running".

Same file, three readers:

| reader | result |
|--------|--------|
| a fresh `bl run` program calling `Ports.list()` | `()` |
| the same program, after decoding one claim WITHOUT `[:safe]` (seeding the atoms) | both claims |
| the gateway VM whose own source mentions `:dest` / `:unix` | both claims |

Why it hides so well: the reader's atom table is populated by its own code, so a reader that happens to mention the atom works and one that does not fails — and the failing reader reports the same thing as an idle machine.

The general lesson: `[:safe]` on a term you also WRITE is a coupling between writer and reader that is invisible in both. If the shape is validated anyway (as here — `%{name: _, port: _, pid: _}` matched in a clause), `[:safe]` buys little for a local, same-uid, 0600 registry and costs exactly this failure mode. Prefer decoding without `[:safe]` and validating by shape, or keep the key set CLOSED and treat a new key as a coordinated change with a migration note.

Corollary for diagnosis: when an entire registry/file set reads as empty but the files are on disk and their owners are alive, suspect the DECODER (atom table, `[:safe]`, a struct/version mismatch), not the writer.
