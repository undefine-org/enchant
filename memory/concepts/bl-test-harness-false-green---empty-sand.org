Two bugs (beam-lisp, fixed 0fe9ad4) surfaced by WRITING an example (examples/sandbox/03), not by a test — the strongest argument for examples-as-verification.

1. HARNESS FALSE GREEN (lib/beam_lisp/test_rt.ex). bl's deftest/is run-state (counters {tests,pass,fail,error} + the current-test ctx slot) was stored env-prefixed via Env.put_key → pfx(env_id(), key). Any assertion evaluated INSIDE (env/with-env fork …) wrote its :fail/:error record under the FORK's env key; run_ns's summary reads under the SUITE env → never sees it. print_report fires immediately (you SEE the FAIL text) but the total says "0 failures". So auth_caps_test.bl reported "8 tests, 0 failures" while 3 assertions were failing AND an empty-caps security hole sat under them. Fix: run-state is per-PROCESS (serial = one process sequential; async = process per file), so it belongs in the process dictionary (Process.put/get), NOT env-scoped ETS. The test REGISTRY stays env-scoped (a forked suite must run only its own tests). After fix auth_caps honestly reports 20 assertions (was 11). LESSON: any "N/N green" from mix beam_lisp.test for a suite that asserts inside env forks was suspect pre-0fe9ad4; only 3 bl files do (auth/*). Re-audited: all genuinely green after.

2. EMPTY SANDBOX CAPS (priv/env.bl + lib/beam_lisp/env.ex). Since W3, auth/caps-for RESOLVES rights to host-ready caps ([:Elixir.String], {File,:read}) — it must, to drop junk module names fail-closed. But sandbox-fork feeds them back through bl env/fork, whose caps-entry expected STRINGS → dropped already-resolved atoms/tuples to nil → EVERY sandbox forked with empty caps (central "enter the token's sandbox" granted nothing). Fix: made caps-entry IDEMPOTENT (atom → passthrough; {m,op} tuple → passthrough; string → resolve). Also split the reflective check from the gate: env/allowed? now uses new Env.reachable?/1 ("touchable for ≥1 op") so an op-scoped grant (File read-only) reports File reachable — WITHOUT loosening caps_allowed?/2 which the compile gate calls with the specific op (loosening there = privilege escalation).

bl gotcha reconfirmed: `count` on a host MapSet returns 1 (sees the struct as one opaque value) — project via (Enum/map c identity) then count, or use (env/allowed? …). erlang/send is the message spelling (send/receive-as-fn are not bl vars; receive is a special form; (after ms body)).
