In beam-lisp, renaming the verifier TIER `:z3` → `:oracle` looks like a pure .bl/content change (examples/oracle/, `bl oracle stats`, tier values in decide.bl/oracle.bl), but the tier value is ALSO a key in an Elixir-side fixed key set: `lib/beam_lisp/z3_ledger.ex` `@tiers [:"native-witness", :z3, :memo]`. `Ledger.record/5` → `canon/1` rejects any key not in `@all = @fragments ++ @tiers ++ [:total]`, raising "unknown ledger key :oracle". Because every invariant-bearing verification records a tier, this one stale atom took down the ENTIRE verify/veritas/corpus test surface at once.

Symptom cascade (one root, three faces): (1) direct "unknown ledger key :oracle" errors; (2) corpus_test walk returned machine names ["?" "?" "plain"] instead of ["acct" "plain" "qm"] — because verify-machine catches the ledger throw and falls back to {:name nil}→"?", so machines WITH invariants (which hit the ledger) lost their names while the invariant-free "plain" survived; (3) 11/13 examples failing. All fixed by the 2-line rename `:z3`→`:oracle` in z3_ledger.ex (the @tiers line + a doc comment).

Doctrine that stays: the MODULE stays `BeamLisp.Z3.Ledger` and prose still says "z3" when describing the actual solver PROCESS (z3 is a real OS port). Only the user-facing TIER NAME and its ledger key become `oracle`. `:tag-lattice`/`:arith`/`:general` are FRAGMENTS (unchanged). z3.bl `:z3-leases` is an unrelated lease-table name.

Lesson: when renaming a value that crosses the .bl↔Elixir boundary, grep the Elixir side for fixed atom/key lists (`@tiers`, `@fragments`, canon/validation sets) — a language-side rename can leave a host-side allow-list stale, and the failure surfaces far from the rename as a validation raise.
