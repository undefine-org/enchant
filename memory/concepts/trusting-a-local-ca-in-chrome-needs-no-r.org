Measured 2026-09-16 on this workstation (Chrome 150 headless, Arch, no root anywhere), against a TLS server terminated by a bl program with a leaf for `probe.test`:

    control, root NOT in the NSS db:
      chrome --headless=new --dump-dom https://probe.test:7799/  ->  net::ERR_CERT_AUTHORITY_INVALID
    after ONE import:
      certutil -A -n "beam-lisp local CA" -t "C,," -i root.pem -d sql:$HOME/.pki/nssdb
      chrome … (same command)                                    ->  the page body loads

So the whole "a dev name over https needs a privileged trust step" premise is false for Chrome on Linux — `$HOME/.pki/nssdb` is the store, `certutil` writes it as the user, and it is per-user, not system-wide. Firefox is the same command against each profile's `cert9.db`; CLI tools take `SSL_CERT_FILE` / `CURL_CA_BUNDLE`; the system store is optional (and `trust anchor` is the one that wants root).

This is what removes localias' (and Caddy's) root requirement from a local-CA design: the CA and its trust import are both user-level. Keep the isolation trick for testing such a change — `HOME=<scratch>` (Chrome's NSS path follows HOME) plus `--user-data-dir=<scratch>` — so a real browser proves the claim without touching the developer's own trust store.
