Symptom: `undefined var: <ns>/<fn>` (or `function BeamLisp.Ns.<Ns>."fn"/N is undefined`) for a fn that IS defined in the .bl source (e.g. auth.biscuit.datalog/encode-block* at datalog.bl:528).

Root cause: BeamLisp.AOT.ensure_loaded/1 (lib/beam_lisp/aot.ex:150) has NO source-vs-beam staleness gate. Loader.ensure_loaded_locked tries AOT FIRST: any compiled .beam with __bl_init__/0 on the code path is used and the .bl source is never read. The only freshness guard is mix compile.beam_lisp's content-hash manifest (_build/<env>/lib/beam_lisp/.mix/compile.beam_lisp, RELATIVE-path keys → {hash, modules}). If a stale beam (compiled before a fn was added) sits in ebin while the manifest still matches current source (up_to_date?=true), the compiler SKIPS it and the runtime silently runs the old beam. → undefined var, only in a full/foreign run, never in a fresh checkout that recompiled.

Reproduced: compiled old datalog source (pre-commit 9bd9840) into ebin, left manifest untouched → attenuate_checks_test threw the exact `undefined var: auth.biscuit.datalog/encode-block*`. Restoring the current beam → green.

Fix/heal: `mix compile.beam_lisp --force` (or `mix clean`) rebuilds from source. Not an auth bug, not a load-order bug — a build-artifact desync. Likely lands via git branch-switch (content-hash manifest ignores mtime; switching branches with a shared _build can leave a beam newer/older than the manifest expects) or a shared AOT cache hardlink.

Gap worth filing: ensure_loaded has no mtime/hash check vs source, so a hand-desynced or branch-switched _build is trusted blindly. Test invocation (mix beam_lisp.test) runs app.start which does NOT force-recompile priv, so stale beams survive into the test run.
