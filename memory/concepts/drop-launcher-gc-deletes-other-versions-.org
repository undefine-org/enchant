** ITEM drop launcher GC deletes other versions' trees under running VMs
:PROPERTIES:
:CUSTOM_ID: CON-drop-launcher-gc-deletes-other-versions-
:KIND: concept
:CONFIDENCE: 0.6
:CREATED: 2026-09-11T21:41:42Z
:END:
:RELATIONS:
:END:
tooling/drop/src/launcher.rs::gc_old_versions removes EVERY version dir under
~/.local/share/drop except the one it is about to use, immediately on extract.

Symptom: a running `bl` aborts with

    Slogan: Can not execute .../drop/<sha8>/erts-<v>/bin/inet_gethost : enoent

plus an erl_crash.dump. It looks transient (re-running works, because the tree
is re-extracted), which is exactly what makes it hard to diagnose.

Mechanism: the VM execs helper binaries (inet_gethost, erl_child_setup, epmd)
out of its own ERTS dir lazily, and a `bl daemon` keeps running from that dir
for its whole life. Any second `bl` with a DIFFERENT payload — a local dev
build beside a released one, or two releases — deletes the other's tree,
killing VMs that are still using it.

Proven 2026-09-11: published bl-linux-x86_64 payload sha 031fae74 vs local
build d9680af6, both under ~/.local/share/drop; the crash dump named 031fae74
while only d9680af6 survived (mtime 1 min later).

Fix directions: GC by AGE (mtime > N days), not by exclusivity; or never GC.
Age-based still loses to a daemon older than N. Docs/native-bundler.md §6.3
specifies the current "keep only this one" behaviour, so the spec changes too.

Blind spot: the release smoke test cannot catch this — it needs two coexisting
payloads. A test would run two drops with different payloads and assert both
still work.
