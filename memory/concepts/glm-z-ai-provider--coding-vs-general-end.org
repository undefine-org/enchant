Added 2026-08-15/16 (commits 1161c4a, e9be8a6). `PROVIDER=glm` → glm-5.3, verified answering live through spell's stack and in the browser.

**The endpoint split is the whole trap.** Z.ai has two OpenAI-compatible base URLs and they are NOT interchangeable:
- Coding Plan key → `https://api.z.ai/api/coding/paas/v4` ONLY
- pay-as-you-go key → `https://api.z.ai/api/paas/v4` ONLY

Proved with a real coding-plan key in one minute: coding endpoint returned a completion; general endpoint returned `{"error":{"code":"1113","message":"Insufficient balance or no resource package"}}`. A fake key returns 401 `token expired or incorrect` on BOTH. So the failure mode is: a perfectly valid key reads as a billing or credential problem when pointed at the wrong half. Default in `spell.provider/providers` is the coding endpoint (glm-5.3 is a coding-plan model).

GLM 5.3 is a REASONING model like kimi — the response carries `reasoning_content` before `content`, and a small `max_tokens` returns `finish_reason: "length"` with empty content. Same generous budget applies.

**Key resolution** lives in `BeamLisp.Spell.Credentials`: environment → `.env` → `~/.spell/agent/agent.db`, never overriding what the caller set. The db table is `auth_credentials(provider, credential_type, data)` with data as JSON; read with `json_extract(data,'$.key')` — a plain `select data` renders `<<$env:S10=…>>` for some rows, which looks like a stored placeholder but is only sqlite3's display of the value (a guard was written against that phantom and removed). db provider names differ from ours: `zai` → glm. `kimi-code` is an OAuth row and must NOT be used as an api key.

Four scripts had each hand-copied the .env loader and three overrode the real environment — that is what made `PROVIDER=fake` silently run against a paid provider and fail as "no provider message arrived".
