beam-lisp coherent reload (priv/reload.bl) is NAMESPACE-LEVEL, not variable-level/additive. The staged source IS the whole namespace: a name the new source no longer defines is genuinely REMOVED on commit (Env.undefine_var), not left shadow-callable. "The whole renaming ethics": rename a fn and every reference must move, because the old name really disappears.

Coherence enforces both faces:
1. same-ns dangling: a reference to a DROPPED var. The trap — the deferred collector reads the LIVE image's public_names as baseline, so a dropped var is still present (until commit) and looks resolved. FIX: call deferred/unknowns-in with an EMPTY defined-set to collect ALL unqualified same-ns call heads independent of the live image, then filter through a namespace-level provides? (for a STAGED ns, only new-source names count; for a non-staged ns, the live image is authoritative).
2. cross-ns removal: a dropped PUBLIC var another live ns still calls. Env.callers_of walks every live var's compiled def AST (ns_defs) for a static dependency on the target. CRITICAL: the compiler emits TWO shapes for a qualified cross-ns call — static {:.,_,[TargetModule,:fname]} (remote call), AND dynamic BeamLisp.Env.fetch!("ns","name") (emitted when the callee's ns is known-but-FORKED, e.g. under the test runner's env/isolated). callers_of must match both or it misses callers in forked envs.

Also: apply-bundle! must declare_ns ALL bundle nses UP FRONT before eval, so a cross-ns qualified call (other.ns/f) compiles as a bl var (Env.ns_exists? true) rather than Erlang interop :"other.ns".f, regardless of eval order within the bundle.

A dropped var with an un-staged caller → :removal error, held. So a rename is atomic across every namespace it touches, or it does not land. Commit 6d2bef2.
