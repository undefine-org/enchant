** ITEM A resident index only helps the doors wired to it

beam-lisp has three code doors — `bl search`, `bl ask`, and the MCP `code/ask` mount — and one owner for the tree's index (BeamLisp.Daemon.IndexWorker + `code.index/ensure-tree`, added 2026-09-14). Two are wired; `bl search` still calls `code.semantic/connect` (= `datom/connect`, "a fresh in-memory store", unconditional) and re-merges the corpus every invocation.

Measured (memo 100% hot, single warm VM — the daemon's own situation): connect 126 ms · index! merge 74 232 ms · query 1 839 ms. So ~74 s of a ~76 s command is corpus assembly, and a warm daemon removes ~2 s of it.

Two traps this exposed:
1. The daemon's "one path by default" (same `run-argv`, verified 0.27 s attached vs 2.1 s cold via the Rust launcher) is about SEMANTICS, not residence. Warmth helps only what reads a conn the daemon owns.
2. `mix bl` bypasses the launcher entirely (`lib/mix/tasks/bl.ex` calls `run-argv` in-process), so benchmarking through `mix bl` can never show the daemon's effect. Benchmark the shipped `bl`, or the daemon path is invisible.

Generalization: when a cache is moved to an owner process, enumerate every caller of the old path — the win accrues only to the callers you migrated, and the un-migrated door keeps paying the full cost while the docs claim otherwise.
