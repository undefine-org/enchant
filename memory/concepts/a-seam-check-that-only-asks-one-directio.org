Reel's board shipped with TWO interactive controls — a text box and an
Add button — while its domain expressed 36 attributes, 27 queries, 7
intents and a 9-edge lifecycle machine. Every test passed. The seam
check reported a clean machine. Nobody noticed until a human opened the
page.

## Why every check was green

`spell.machine/unhandled-fires` asks: does this fire LAND? A page that
barely fires anything passes it completely — every fire it makes is
handled, precisely because it makes so few. The inverse question — what
does the server OFFER that no control can reach — did not exist.

`move`, `judge` and `record` were declared in the contract, written
correctly, and wired to nothing. 4 of 5 events unreachable, zero
findings.

∴ **coverage is a two-directional property of a seam.** Asking only
"is every call answered?" cannot distinguish a complete UI from an empty
one. The missing check is a set difference over data both halves already
expose (`spell.seam/events` × `machine/view-fires`) — 15 lines, and it
named all four dead handlers in seconds.

Severity: WARNING, matching `unrendered-assigns`. A handler may
legitimately land before its control while a page is grown one
definition at a time. But it must be PRINTED — `check.exs` reported
"0 errors, 8 warning(s)" and passed, and that bare count was the only
trace. A count nobody reads is silence with a number on it.

## The test seam that did not exist

`domain_test.exs` passed 48/48 against a board with no controls, and it
could not have failed: a domain test calls `intent/perform` directly,
which is the layer BENEATH the control a person needs. So a UI with
nothing on it satisfies every domain test ever written.

The fix is a test file that reads the VIEW TERM — what a browser is
handed — and asserts the two directions against each other. That file
is what turns "every declared event is reachable" into a property the
suite enforces rather than a thing someone remembers to check.

## Three bugs that all answered nil

Wiring one control exposed a chain, each invisible for the same reason:

1. `task-rows` computed `:slug`; the template dropped it. So the DOM
   carried `data-key`/`data-index` — positions in a list that re-sorts
   on every write. `(fire :move @slug …)` had nothing to read: the
   handlers were not missing buttons, they were UNWIREABLE.
2. The handler read `@role`, a page-local signal living in the BROWSER.
   A handler body runs on the BEAM and its env binds its own params and
   nothing else, so the name resolved to nothing.
3. Passed as a param, the body writes `{:role role}` — a KEYWORD key —
   and the reader looked up the string `"role"`.

None raised. All three answered nil, and nil was a legitimate value
meaning "nobody said", so the board rendered the default lead's
affordances and looked entirely healthy. **A wrong answer
indistinguishable from a right one is the expensive kind.**

## Two compiler limits found only by clicking

- `spell.contract/emit-html` accepts an element, text, or a hole and
  throws "not markup" on a nested `(st/each …)`. A row cannot render a
  list of its own; it needs FIXED SLOTS fed by an already-positioned
  projection.
- `fire` prefixed EVERY argument with `$`, so `(fire :judge @slug
  "ready")` emitted `$ready` — a signal nobody declares, evaluating to
  nothing. The server then refused the event with a perfectly correct
  domain message: `A component is one of: missing, partial, ready. Not
  "".` A compiler bug wearing a domain error's clothes, which sends you
  to read the validation — which is right, and was never the problem.

Also: a `@x` written into a shell template emits a hole nothing binds,
and the browser paints the literal text `` `$x` ``. A shell is static
HTML rendered once, never invoked — which is exactly why the machine
reports it as a dead template. A subscribed value reaches the DOM by
being MOUNTED (`st/view`), and a boolean hole in an attribute position
renders as the empty string, carrying no information while looking like
it does.

## The rule

An empty list is an ANSWER and must say which answer it is. Reel's
product panel — "what is not proven?", the question the tool exists to
ask — rendered a heading and blank space when every requirement was
proven: the best possible result, displayed exactly like a crashed
query. A person cannot tell those apart, and assumes the bad one.
