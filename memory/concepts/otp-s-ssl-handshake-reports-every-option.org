`ssl:handshake/2,3` (the upgrade path — hand a socket accepted by `gen_tcp` to `:ssl`) wraps its body in

    catch error:{badmatch, _} -> {error, {dtls_upgrade, notsup}}

and that catch also swallows a failed `ssl_config:handle_options/4`. So ANY bad option list is reported as "DTLS upgrade not supported", which reads as "bl/this VM cannot do TLS" and is wrong. Verified 2026-09-16 on OTP 29 (`/usr/lib/erlang/lib/ssl-11.7.1/src/ssl.erl`, the `dtls_upgrade` clause sits right after `{ok, Config} = ssl_config:handle_options(...)`).

Corollary that caused it in beam-lisp: the option list must be a REAL Erlang list when `:ssl` sees it. In bl, `(concat (to-list a) (list b))` yields a bl list; at the FFI boundary it must be `(to-list …)` again. Symptom without it is `error: no function clause matches` (the `is_list` guard) for `:ssl.listen`, and the DTLS lie for the handshake/upgrade path.

What works from bl, once the list is real and `(Application/ensure_all_started :ssl)` has run:
`(ssl/listen port opts)` → `(ssl/transport_accept ls t)` → `(ssl/handshake s t)` → `(ssl/recv …)`/`(ssl/send …)`. Verified serving HTTPS with a CA-issued leaf whose chain `curl --cacert` and `openssl s_client` both return "Verify return code: 0 (ok)".

Rule: when a failure sentence comes from a library that catches broadly, unwrap and print the REAL reason (`ssl_config:handle_options` returns `{error, {options, …}}`) rather than echoing the library's message.

Corrected 2026-09-17 by direct measurement (the first version of this note guessed the cause).

`ssl:handshake/2,3` (the upgrade path — hand a socket accepted by `gen_tcp` to `:ssl`) wraps its body in

    catch error:{badmatch, _} -> {error, {dtls_upgrade, notsup}}

so **every** `badmatch`/raise inside it is renamed to "DTLS upgrade not supported" — which reads as "this VM cannot do TLS" and is wrong.

What actually triggers it (measured, OTP 29, `ssl_config:handle_options/4` called directly with each shape):

| options argument | result |
|------------------|--------|
| the CA's own list | `{:ok, config}` |
| that list + an UNKNOWN option `{:frobnicate, true}` | **`{:ok, config}`** — OTP accepts unknown options silently |
| that list + a nonsense VALUE for a known option | `{:ok, config}` — same |
| a value that is **not an Erlang list** (`is_list/1` → false) | **raises `FunctionClauseError`** → renamed `{dtls_upgrade, notsup}` by the handshake |

So the lie is about the SHAPE of the argument, never the client and never the option contents. In beam-lisp the way to produce it is a list built by `concat` (a bl value) crossing the FFI boundary — the fix is `(to-list …)`.

Corollaries, each measured:

- a legitimate failure keeps its reason: `ssl:handshake` on a peer that connects and says nothing returns `{:error, :timeout}` — printable as-is;
- after a failed handshake the socket is unusable (reusing it returns `:error`) — close it, do not retry;
- `:ssl.listen`/`transport_accept`/`handshake` all work from bl once (a) the options are a real list and (b) `(Application/ensure_all_started :ssl)` has run; a missing `:ssl` app shows up as `ssl_listen_tracker_sup` not running, not as an option error.

Rule: when a library catches broadly, print the REAL reason (here: call `ssl_config:handle_options/4` yourself) instead of echoing the library's message.
