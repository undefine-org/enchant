## The rule

When a language exposes a predicate in two positions — as a function
`(pos? x)` and inside a guard `:when (pos? x)` — the two MUST answer
identically for every input. A guard form that is subtly narrower is not a
safe approximation; it is a trap. Code reads as a mechanical refactor of an
`if` into a clause head and silently changes behaviour.

## How it goes wrong (observed, beam-lisp, 2026-08-22)

Implementing `:when` guards, I mapped beam-lisp predicate names onto
guard-safe BIFs. Three of the mappings were wrong, ALL IN THE SAME
DIRECTION — the guard was narrower than the function:

| predicate | function says | my guard said | why I got it wrong |
|---|---|---|---|
| `fn?` | true for `{:"$blfn",…}` and `{:"$remote",…}` tagged fns too | `is_function/1` only | reached for the obvious BIF without reading `RT.fn?/1` |
| `map?` | true for RECORDS and sorted maps (a record IS a user-facing map here) | excluded every struct | copied the `is_bl_map/1` invariant, which exists for a DIFFERENT layer where records are routed by an earlier clause |
| `pos?` | `x > 0`, BEAM total term order, so `(pos? :k)` is TRUE | added an `is_number` conjunct | "made it safer" — invented a semantic the language did not have |

The `map?` one is the instructive failure: `is_bl_map/1` is a real,
correct, well-documented invariant. It was simply an invariant about a
different dispatch context. Reusing a guard because it is named for the
concept you have in mind, without checking what the concept means AT THAT
LAYER, is how a correct abstraction produces an incorrect use.

The `pos?` one is the seductive failure: adding `is_number` looks like
pure hardening. It cannot raise either way (BEAM comparison is total), so
the conjunct bought nothing and cost agreement.

## The check that catches it

Do not assert guard results against hardcoded expectations — that just
re-encodes your assumption. Assert the guard form against the FUNCTION
form, over a value list spanning every type kind:

```clojure
(defn m? ([x] :when (map? x) true) ([_x] false))
(map (fn [v] (= (m? v) (map? v)))
     [{:a 1} [1 2] (atom 1) (->Record 1 2) (sorted-map :a 1)
      (fn ([x] x) ([x y] y)) inc 1 -1 :k "s"])
;; every element must be true
```

This finds divergence without needing to know the right answer in advance,
which is the point — if I had known the right answers I would not have
written the bug.

## Generalisation

Applies to any dual-position construct where an "optimized" or
"restricted-dialect" spelling shadows a general one: guard vs function,
compile-time vs runtime evaluation, macro-expansion vs call. The restricted
form is allowed to REFUSE inputs (that is what makes it restricted); it is
never allowed to ANSWER DIFFERENTLY.

Corollary for review: when several such mappings are written in one batch,
check them as a set. Mine were wrong in a consistent direction, because a
single mistaken instinct ("guards should be conservative") produced all
three. One wrong mapping is a typo; three wrong the same way is a wrong
premise.
