Three shapes that cost a round trip each while writing a real bl service (measured 2026-09-16, beam-lisp).

1. `(erlang/apply Mod :fun (list a b c))` SPLICES the list as the argument list — it is `apply(M, f, [a,b,c])`, and `(list x)` where x is already a list collapses, so you cannot pass a single LIST argument that way. Observed: `:maps.from_list` called with arity 2 (a 2-pair list) and arity 9 (a 9-pair list). Workaround: build maps as literals instead of `from_list`. `{:name NAME :port 0 :hosts (list HOST) :dest (tup (list :unix P))}` produces a real Erlang map with ATOM keys — `:erlang.term_to_binary({:a 1})` is 11 bytes, exactly MAP_EXT with one atom key, so the values survive `binary_to_term` in ANOTHER VM as plain maps (which is how a claim file written by one process is read by another).

2. `:erlang.list_to_integer/1` takes a CHARLIST, not a binary. `(System/get_env "X")` gives a string → `(erlang/list_to_integer s)` is an argument error; use `String/to_integer`. (`(erlang/list_to_integer (os/getpid))` is correct precisely because `:os.getpid()` returns a charlist.)

3. A literal vector round-trips through messages: `(erlang/send p [:go sock])` is matched by `(receive [:go s] …)`. That is the hand-off primitive a bl accept loop needs (see the controlling_process concept).

Also worth knowing, not FFI: `web/serve {:port 0 :ip {:local path}}` serves a whole Plug app over a unix socket — Bandit logs `at <path> (http+unix)`.
