It is the same destination by the opposite route on every privilege question: on macOS the proxy runs as root (sudo subshell); on Linux the documented fix is `sudo setcap CAP_NET_BIND_SERVICE=+eip $(which localias)`, which its docs say must be redone "after installing or upgrading" — the capability dies with the inode. Names also need root (hosts file). And it has no fallback: if 80/443 are busy the daemon simply does not start ("daemon is not running").

Two things this settled for us. (1) `setcap` cannot suit `bl` at all — our launcher IS the artifact, so every install replaces the file the capability was attached to; our loopback nftables redirect names a port and a table, no path of ours, and survives upgrades, which is exactly why it is the right mechanism here rather than a stylistic preference. (2) Their docs never have to explain what the redirect takes away, because binding 80 directly takes nothing: that is the one real advantage of being the process that holds the port. Ours had to say it — a server already answering on 80 loses loopback :80 while the rule is in — and it did not, until this. Hence `answer_on?/2` returning `:ours | :other | :closed` and the three sentences in `port_80_advice/1`, with a proof run showing a foreign `http.server 80` losing the port and getting it back on removal.

TLS stays the real gap (FUP-051): their answer is 443 + a local CA, and the same redirect rule grows `tcp dport 443 redirect to :<tls port>` so our gateway stays unprivileged while a name becomes an https origin.
