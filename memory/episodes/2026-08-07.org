** ITEM Bug: atom-table exhaustion hazard in reader
:PROPERTIES:
:CUSTOM_ID: EP-9382eb7dc4d669a4
:KIND: episode
:CONFIDENCE: 0.6
:CREATED: 2026-08-07T22:13:20Z
:END:
:RELATIONS:
ABOUT: PLAN-009-bug-atom-table-exhaustion-hazard-in-read
:END:
PARTIALLY DONE — commit bfb4179. Investigation corrected the premise: the READER never interns atoms (it has returned {:symbol, name}/{:keyword, name} with plain STRING names since wave 3); all ~15 String.to_atom sites live in compiler.ex and rt.ex. Empirically confirmed the hazard is real and severe: filling the atom table aborts the whole VM ("no more index entries in atom_tab" + crash dump) — uncatchable by try/rescue. Chose mitigation (1)+(3) from the plan: trusted-code position, documented in docs/trust-boundary.md, plus a cheap guard at the reader (the one choke point every source text passes): every :atom_check_interval (default 256) symbol/keyword tokens, compare :erlang.system_info(:atom_count) against :atom_limit at :atom_high_water_fraction (default 0.9) and raise a catchable BeamLisp.Reader.AtomLimitError naming the token. Counter+config in the process dictionary, reset per read (no leak, no cross-process race). Read-path cost: 396.4ms → 393.2ms on a 1.5MB source (~40k tokens) = noise. REMAINING (why this is not fully closed): the guard samples the ABSOLUTE VM atom count, so a single hostile read into a fresh VM that interns ~1M new names can still exhaust the table mid-COMPILE. Full coverage needs the same high-water check at the compiler/rt intern sites; also worth preferring String.to_existing_atom with fallback for REPL keyword re-reads. Keeping this item open at ITEM state for that follow-up.
