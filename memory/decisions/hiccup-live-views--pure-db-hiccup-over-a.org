PLAN-052. A "better than LiveView" reactive UI for beam-lisp, designed against verified repo mechanics.

CORE THESIS: LiveView invented `assigns` because it had no db under the socket. beam-lisp HAS the log, so: a view is a pure fn `db→hiccup`; an event is a fact (closed vocab `[:assign]`/`[:intent]`/`[:navigate]`); socket state is a session-scoped in-memory datom conn (conn:db :: atom:value — deref/swap!/add-watch/as-of already literally map). The DOM diff rides on fact-deltas gated for soundness by priv/live.bl register-live! (monotone or refused by name).

THE ELEGANT COLLAPSE (sharpest point): auth/guard injects a CONJUNCTIVE :where clause = monotone by construction. live.bl requires monotone for sound incremental diffs. ∴ the property that makes an incremental view SOUND is the same one that makes it SECURE. auth/guard ∘ datom/watch (examples/datom/live/08-guarded-feed.bl) already proves a feed "cannot deliver a fact the guard excludes." One concept, two payoffs.

VERIFIED MECHANICS (probes, 2026-08-29): (R1) a macro emits defserver cleanly → defview/deflive are macros, no compiler change. (R2) session conn inside a defserver init via connect-with(store-ets/open) + listen! WORKS, self-cleaning on disconnect (ETS table owned by socket process). (R3) ^{:key} reader metadata is DROPPED on vectors at runtime → use :key as a reserved attr in the attr map, stripped before HTML. (R4/R5) reader parses :div#app.a.b as ONE keyword (# and . not delimiters); split is literal. (R6) patch ops → clean JSON via existing interop/->json. (R7) shared+session composition = explicit two-value (board shared-db session-db locals), NOT store-overlay (overlay wants one base store). (R8) headless tests = .bl files, test socket captures push! into a pid, the watch_test.bl precedent.

SCOPE BOUNDARY (R0, load-bearing): mix.exs says "beam-lisp is the language again; contract/view stack lives in the spell repo :interface app." No Phoenix/web here. ∴ the WHOLE server side (pure renderer W1, differ W2, defview/deflive+socket+auth W3, composition W4, examples W6) is buildable AND provable in-repo with .bl tests. Only the ~100-line JS client + real Phoenix channel (W5) is downstream spell-repo work — spec'd here (wire contract + golden JSON fixture + apply-ops reference semantics) but not browser-verifiable here. Stated honestly, not hidden.
