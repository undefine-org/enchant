Q: should the committed bootstrap seed (priv/bootstrap/seed/, 30 .beam, 2.4 MB) be Core Erlang text that OTP compiles at boot, instead of bytecode? **No** — measured 2026-09-11 on OTP 29, priv/boot/lower.bl (2 modules, 163,340 B of beams):

1. SIZE. `core_pp` is a printer, not a serializer: its output for those two modules is 128,965,303 B = **790x** the beams (blow-up is the paper algorithm's indentation — whitespace-only lines up to ~29 KB; `Ns.*` shims' `__bl_init__` nests deepest). Whitespace-stripped: 993,547 B = **6.1x**. 18 of 30 seed modules had produced 515 MB when the run was killed.
2. FIDELITY. `core_pp` output does NOT read back: `core_scan`/`core_parse` fail `syntax error before: '-'`, because the lowering names Core vars after Lisp locals/gensyms (`and-tmp#` -> `_and-tmp__107__c_108`, `catch-clauses` -> `_catch-clauses_90`) and Core Erlang's variable grammar has no `-`; the printer emits them bare. Synthetic cerl modules DO round-trip byte-identically (core_pp -> core_scan/core_parse -> compile:forms, 404 B identical), real ones do not. A .core seed would need its own writer + name discipline + conformance test = new code on the path that must never fail.
3. LADDER UNCHANGED. Staging exists because a previous generation's `__bl_provenance__/0` key != current toolchain key and `AOT.stale?/2` must not route it to the genesis-less source path (`:bootstrap_staging`). That is a property of the program, not the encoding — text-compiled seed modules still report the old key. No simplification.
4. BOOT. install! is a sha256-verified copy today; a text seed must be scanned (measured ~72 ms per 93 KB), parsed and compiled for the whole tier before the first form runs.

Buys: a readable floor (nobody reads ~6-15 MB of machine-generated Core Erlang; the seed is never edited and is superseded by the rebuild). Auditability is WEAKER than the status quo: beams are byte-identical to what the current source produces (aot_reproducible_test.exs) and gen_manifest refuses to publish a manifest whose stamps disagree. One real advantage: OTP-version robustness (text always compiled by the running OTP). Not worth a permanent codec on the bootstrap path.

The real itch (seed written into ebin alongside build output, told apart by provenance/mtime/staging) is PLAN-088 territory: load the seed from memory without landing it in ebin — available to beams just as well.

Recorded in docs/from-source-to-silicon/05-the-seed.bl.org ("Why the floor is bytecode, not Core Erlang text") + docs/self-hosting.md pointer.
