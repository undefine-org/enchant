#+title: Foundry-backed Nix execution experiment — results and decision
#+date: 2026-10-25
#+state: Experiment passed; infrastructure redirection recommended; production migration unimplemented

* Decision
Make Foundry's existing process/data interface the starting point for a Nix
artifact backend. Delegate immutable artifact production to Nix and Linux
external-job lifecycle to systemd. Keep compiler semantics, execution admission,
callback/actor lifetimes, descriptors and in-VM generation retirement in BL.

This is enough evidence to redirect the infrastructure portion of the ongoing
execution work. It is not evidence to remove its implementations immediately,
close its historical cases, or claim that all remaining work is solved.
Read PLAN.org for the incremental replacement gates and CAPABILITIES.org for
the proposed product experience. HANDOFF.org is the message for the other session.

* Actual prototype
A dependency-free real Cargo crate exports answer() from a cdylib. The Nix
recipe pins existing store tool paths and generates its source from a typed
integer input. Cargo runs offline and locked with a private target directory.
The result is a library and schema-versioned JSON manifest. Python ctypes
loads the real library and checks its answer and SHA256. BL invokes the fixed
request recipe through the real Foundry executor, decodes Nix JSON, reads the
manifest and checks the returned answer. No fake Cargo or compiler is used.

The prototype is intentionally host-specific: x86_64 Linux, absolute existing
store tool paths, and an experiment-only scratch path in bridge.bl. A production
backend must use derivation dependencies from the pinned flake, source filesets,
complete request/result contracts, target inventories and explicit retention.
The answer parameter is not a complete real-world source/ABI dependency closure.

* Results
results.json contains ten passing controls:
| Control | Observed result |
| Identity and reuse | Same request returns same store path; answer 43 changes path, bytes and actual loaded behavior |
| Concurrent requests | Two independent clients return one output; retained Nix log contains exactly one builder-start marker |
| Requester death | Kill the actual Nix client after builder-start; a new request obtains a valid product |
| Descendant after builder exit | Child is confirmed ready, closes descriptors 3–9, and attempts a delayed output write; no late write appears |
| Causal negative | Same unsupervised delayed writer writes successfully after its parent shell exits |
| Failed build | A deliberately failed candidate is refused; previously valid output remains usable |
| Explicit retention | Register a real indirect GC root, query it, remove it, confirm that reference is gone |
| systemd descendant cleanup | Actual child calls setsid; kill service main; pidfd confirms descendant termination |
| Filesystem isolation | An existing host-side canary is absent from the real Nix builder view |
| Request refusal | Wrong argument type and unexpected JSON field refuse before artifact acceptance |

bridge-result.json separately records a successful actual BL -> Foundry executor
-> Nix -> manifest -> BL round trip, twice in one VM. A unique request token
forces the first tiny library build, then the second reuses its exact output.
First request: 241ms. Warm request: 22ms. Cold bridge service: 1.217s,
119.8M reported peak, zero swap. Ten-control service: 17.666s, 25.3M reported
client-tree peak, zero swap. These are single observations, not benchmarks or
predictions for full compiler builds. Concurrent requests took about five seconds;
no inference of a latency win is made for that case. The isolation case reused
a prior result in the final pass; its first actual build also passed.

The systemd client caps do NOT include workers in the separate Nix daemon.
Nix was sandbox=true, sandbox-fallback=false, use-cgroups=false. Python build
requests selected one local job/core and a 35s builder timeout; the BL build
used a 30s client deadline. No claim of whole-build memory enforcement is made.
Establish daemon worker containment before using large workloads.

* What the experiment does not establish
- Client death is not cancellation. The test accepts legitimate daemon-owned
  continuation or safe restart, and does not distinguish them. A production
  shared-request cancellation/reference policy remains to be tested.
- The Nix delayed-write observation proves output stability over its window,
  not a universal descendant-death proof. systemd death is separately observed.
- Retention registration is tested; actual garbage collection, last-root races,
  and realm-crash cleanup are not. No global collector was run.
- No full compiler artifact generation, B/C reproduction, mandatory NIF loading,
  SDK, native ABI matrix, remote worker or non-Linux product was qualified.
- Result manifests are prototype checks, not authenticated runtime admission.
  Tampered product/manifest refusals, target binding and loaded ABI identity
  must be enforced and tested in the real consumer.
- No Foundry codec round-trip, native codec build or generated Nix host deployment
  is claimed. Existing codec evidence remains separate.

* Findings that affect implementation
1. Existing Foundry argv execution can carry a data request without shell
   interpolation. Use a fixed recipe with a closed JSON request schema.
2. Foundry normally merges stderr into stdout. Nix progress breaks naive JSON
   decoding on a fresh build. Its existing private stdout-file option separates
   machine results; the final bridge exercises a fresh build using this option.
3. Existing store packages must retain Nix string context. In this raw prototype,
   coercing path literals copied packages as source directories, losing the
   expected runtime closure. builtins.storePath fixed the fixture. Production
   should interpolate actual pinned derivations, not reconstructed path strings.
4. Minimal sandbox shell packages are not full tool environments. Explicit
   coreutils was needed. This is useful evidence for declaring all build inputs.
5. Foundry's process-group executor is useful plumbing, but process groups alone
   cannot contain setsid descendants. Reuse its data API while adding a real
   cgroup-backed job adapter; do not treat its group cleanup as the final boundary.
6. systemd expands dollar syntax in command arguments unless disabled. The
   fixture sets --expand-environment=no. Passing arbitrary shell scripts as
   service arguments is not the proposed production request interface.
7. nix eval --file can return a lambda without exercising assertions. The
   negative request gate uses nix build to force actual request application.

Early fixture failures remain in attempt1/2/3.json; they are not product
regressions. The final ten-control run passed after repairing the fixture.
A smoke check also diagnosed store-path coercion before the final run.

* Reproduction
Fixtures are recorded verbatim in fixtures/. Python scripts resolve their local
fixture directory. bridge.bl intentionally refers to the original scratch path;
copy fixtures there before replaying the bridge, or update its explicit paths
and record a new fixture identity. The store tool paths must exist on the host.

Run experiment.py and supplement.py sequentially under a named, bounded
systemd user service. Run bridge.bl once under the recorded frozen runtime,
with -p /home/othman/code/undefine/foundry/src/foundry/support. Read scripts/bl-mem
first. Do not invoke the changing checkout compiler just to replay this boundary.
Final JSON receipts and inputs.json are the reviewable evidence. Tests clean up
owned client processes, the private GC root and the supervisor test service.
Small ordinary unrooted Nix outputs remain for normal store GC.
