#+date: 2026-10-25
#+state: Proposed experience; only the adjacent prototype's receipts are implemented evidence

* Experience in ordinary development
Keep existing verbs: edit a project, run ./bin/bl, build, test and inspect the
realm. A warm analysis/compiler VM continues serving interactive requests.
When a native/toolchain/compiler artifact is needed, the artifact provider asks
Nix for the exact declared product. Foundry displays preparation progress,
result identity and failure details. A repeat request reuses an immutable output.

An application-only edit should not rebuild Rust, OTP or the launcher. A native
edit prepares a new product while existing execution keeps its previous one.
The runtime's own ABI/admission checks decide whether the new product can enter
that VM or requires a fresh process. No promise of hot-swapping arbitrary NIFs.

Two sessions can request the same artifact without negotiating a shared mutable
native destination. Their interactive state remains private. Cancelling one
request must not cancel another session's subscription; this is a required next
backend gate, not a capability already demonstrated by the prototype.

Build failure leaves the selected working artifact intact. The UI shows whether
failure occurred during preparation, qualification, activation or readiness.
A code rollback selects an earlier compatible closure; data restore/migration
remains a separate operation. A disconnected UI can reconnect to a daemon-owned
build once the production job/observation contract exists.

The actual experiment is smaller: bridge.bl sends JSON {"answer":42} through
Foundry deployment-exec to a fixed Nix recipe and checks the returned manifest.
The production API must include all real semantic inputs; hashing incomplete
requests only makes an incomplete cache look authoritative.

* Proposed user-facing features
| Capability | Day-to-day benefit | Additional work / dependency |
| Prepared environments from declarations | Open a project and prepare its exact native/tool dependencies without ad hoc PATH fixes | Complete project-to-request projection; missing/unsupported dependency diagnostics |
| Native reuse across sessions | Other sessions use a ready artifact rather than recompiling Rust | Common provider; retention and shared-subscriber semantics |
| Comparison realms | Run the same application against two compiler/native closures | Realm launcher, separate state, compatibility and resource limits |
| Reproducible failure capsule | Share a failing source/test/runtime identity instead of a mutable directory | Snapshot/export tool, exact receipt format, private-input handling |
| Dependency explanation | Explain why a source change invalidates one artifact or changes a toolchain | Join language dependency facts with Nix derivation dependencies; preserve unknown edges |
| Candidate preparation in background | Continue using the working generation while another is built and checked | Durable job observation and safe activation protocol |
| Remote builds and reusable results | Prepare expensive artifacts on the configured builder | Target-compatible workers, cache trust, deployment-specific request policy |
| Agent-safe experiments | Agents prepare private candidates without rewriting selected runtime artifacts | Job admission, quotas, bounded scratch storage and immutable selection |
| Compiler regression bisection | Test identical inputs against retained compiler generations | Comparison runner and deterministic test selection |
| Code rollback with inspectable compatibility | Select a known prior release and see its data-compatibility limits | Existing Foundry handover integration; data-basis rechecks |
| Offline prepared workspaces | Continue supported work with retained complete dependency closure | Explicit export/root policy; no claim that unfetched inputs work offline |
| Resource-aware build queue | Avoid a swarm of cold BEAMs exhausting the host | Actual daemon-worker accounting, queue policy and measured estimates |
| Toolchain/ABI impact preview | See a compiler, libc or native change before activation | ABI/product inventory and target-specific consumer gates |
| Recorded environment changes | Review generated Nix changes with preserved comments | Reuse Foundry codec and existing approval boundaries for actual host changes |

* Less obvious opportunities
- Join source impact with artifact impact: a language-level dependency query can
  explain which stored products, tests and deployment candidates depend on it.
  A Nix edge alone cannot recover lexical/macro/callback semantics.
- Prepare native extensions from ordinary BL declarations, reuse remote products,
  and expose their qualification state without asking users to manage Cargo caches.
- Preserve multiple compiler generations as ordinary retained artifacts, which
  enables controlled migration experiments and executable historical bug reports.
- Use one candidate identity through preparation, tests, deployment and runtime
  observation, while retaining separate semantic and operational identities.
- Share build results across agents without sharing mutable environments, giving
  parallel research a lower coordination cost once resource admission is in place.

* Limits that remain visible in the product
Nix is a build-host capability; shipped drops can remain self-contained.
Store integrity is not proof of compiler correctness or permission to execute.
Filesystem roots do not replace in-VM generation pins. Rollback does not restore
data. A ready native library does not mean it is safe to load into an old VM.
These distinctions should appear where users decide activation/compatibility,
not as implementation trivia in every ordinary build interaction.
