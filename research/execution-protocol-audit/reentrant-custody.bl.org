#+title: A claim marker is data; an open kernel lock is custody

* The missing check
The former claim/owned? accepted any non-nil process-dictionary value. A copied,
closed or fabricated handle could make a nested build report successful admission
without acquiring kernel custody. release! also removed the diagnostic before
validating that the handle belonged to this workspace.

The native claim resource is minted only after writer exclusion, exclusive
follower exclusion and atomic publication of a fresh native-generated cohort.
The follower barrier stays held through publication. Callers provide descriptive
text, not the nonce. A generic file lock, even a genuine exclusive descriptor
owned by the current process at the right anchor, cannot certify admission.
Diagnostic publication replaces a preexisting symlink instead of following it.

nif_file_claim/3 performs that admission. nif_file_claim_owned/3 requires the
admitted resource kind, live monitored exclusive custody, the current BEAM owner,
the current Unix anchor inode and the expected diagnostic scope. Its authority
comes from the actual native resource; removing diagnostic text does not revoke
custody or prevent cleanup. This Unix identity profile refuses other targets;
target qualification remains required. Inspection performs no file creation.

claim/owned? checks this actual resource. claim/release! verifies it before
removing diagnostic text or closing it. The native unlock itself also refuses
a foreign caller while a process-owned descriptor is live. Closed descriptors
stay idempotent; unmonitored resources preserve existing VM-generation lifetime
and release semantics. os.lease transfers its business owner while its keeper
remains the actual native descriptor owner.

The check observes current custody; it does not authorize arbitrary paths or
Source invocation. Permanent anchors must never be unlinked by SDK writers.
This is not a sandbox claim for arbitrary trusted native plugins.

* A nested build keeps one descriptor and one cohort
Run this cell on the changed component host/NIF or the completed batch2 artifact.
The installed earlier C does not yet export the new native predicate.

#+begin_src beam-lisp :id actual-reentrant-custody
(ns execution.reentrant.walkthrough (:require [claim :as c]))
(let [root (Path/join (System/tmp_dir!) (str "claim-example-" (erlang/unique_integer (list :positive))))]
 (try
  (assert (:ok? (c/acquire! root "outer builder")))
  (let [record (File/read! (c/path-for root))]
   (assert (c/owned? root))
   (assert (:ok? (c/acquire! root "nested build")))
   (assert (= record (File/read! (c/path-for root)))))
  {:nested-admission :same-kernel-custody :native-identity (BeamLisp.LazyMemo/runtime_identity!)}
  (finally (c/release! root) (File/rm_rf! root))))
#+end_src

* Evidence and remaining obligations
The actual Source-derived marker-only mutation admits a competing writer while
normal admission refuses it. Filesystem tests cover real valid/closed/forged/
foreign/shared/unmonitored/wrong-anchor resources, aliases and anchor replacement.
Native-only boot, original child custody, lease transfer/death, direct build
refusal and the collector's rebuilt native ABI are checked separately.

These are component receipts, not a reproduced SDK or final artifact. The new
filesystem boundary maps every direct claim/lock consumer before batch2 freeze.
Record and supervisor metadata boundaries retain their separate required exits.
claim/clear! and store install/sweep writers remain explicit open audit work;
this handle repair does not establish their exclusion or path scope.
