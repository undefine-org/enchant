#+TITLE: Intern contexts across managed starts and transitions

* Context data follows code custody

Managed pending starts and owner transitions now store a native graph ID and
an interned context ID. Their rows no longer store the full generation or a
context map. Capture replaces the original generation with its frozen ID before
the request enters Env. Ordinary overlays remain bounded and are interned in
the same existing pool used by callback registrations and invocation frames.

The native owner allocates context and code custody together, undoing partial
allocation on refusal. No supplied graph selector, context ID or Source callback
can create a starter. A child first claims its genuine starter receipt, receives
the context ID, then resolves the overlay and obtains the original graph directly
from the shared immutable snapshot. The graph does not travel back through the
Agent reply. Launch compares the original native graph IDs; native ownership
and handoff still authenticate the exact receipt, class, PID, lease and graph.

Private pending rows can be observed below only as native test diagnostics.
Their IDs do not confer execution or starter authority.

* Two pending starts share one context

#+begin_src beam-lisp :id pending-start-shared-context
(ns execution.start.contexts.walkthrough (:require [reload.generation :as g]))
(let [graph (g/prepare! {:application-id "start-context-walkthrough"
                         :sources {"start.context.demo"
                          "(ns start.context.demo) (defserver owner (init [_] (ok nil))) (defn class [] owner)"}})
      parent (erlang/self)
      creator (spawn #(g/with! graph
                        (fn []
                         (let [class (g/invoke! graph "start.context.demo/class" [])
                               a (BeamLisp.Env/begin_server_start! class)
                               b (BeamLisp.Env/begin_server_start! class)]
                          (erlang/send parent [:start-contexts a b])
                          (receive :finish :done)))))]
 (try
  (let [[a b] (receive [:start-contexts a b] [a b] (after 15000 (throw :start-context-timeout)))
        left (BeamLisp.Env/server_start_row (elem a 2)) right (BeamLisp.Env/server_start_row (elem b 2))
        shared (and (some? (:context-id left)) (= (:context-id left) (:context-id right)))
        copied (or (contains? left :generation) (contains? left :context))]
   (assert shared) (assert (not copied))
   (erlang/send creator :finish)
   (let [reclaimed (loop [left 1000]
                     (cond (and (nil? (BeamLisp.Env/server_start_row (elem a 2)))
                                (nil? (BeamLisp.Env/server_start_row (elem b 2)))) true
                           (zero? left) false
                           :else (do (Process/sleep 5) (recur (dec left)))))]
    (assert reclaimed)
    {:shared-context shared :copied-generation-or-context copied :creator-death-reclaimed reclaimed}))
  (finally
   (erlang/send creator :finish)
   (when (Process/alive? creator) (Process/exit creator :kill))
   (g/retire! graph))))

* Release only at the original boundary

A creator dying before launch reclaims pending code and its context reference.
Claimed/uncertain launches keep both until the existing exact handoff or actual
child death. A transition keeps its context through accepted, prepared and
uncertain phases. Completed commit or authoritative abandonment releases the
row's reference; an active invocation frame independently retains its context
until unwind. Completed reconciliation receipts carry neither code nor context
custody. Closing data alone cannot assert an unknown effect completed.
