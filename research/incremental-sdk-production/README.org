#+title: Incremental production SDK cutover, 2026-10-30

* Diagnosis

At commit bff7ef25, nix/bl-drop.nix supplied the same broad src to dependency
compilation, compiler qualification and SDK packaging. That source included
ordinary SDK libraries and native crates. A library edit therefore changed
all three derivations. Dependency setup also depended on the complete native
bundle. A sibling native edit could invalidate the compiler product.

Each new Nix worker began with an empty mutable cache. The compiler's old
local cache and the build planner's namespace keys could not cross that worker
boundary. SDK production used a whole-inventory preparation profile and
exported no raw per-unit predecessor for the next derivation. Nix correctly
rebuilt the excessively broad products its recipes described.

Rust vendoring preserved downloaded sources, not compiled dependencies.
The native recipe therefore recompiled external crates after a body edit.
When target artifacts were first exported, Cargo still rejected them because
the Nix cargo setup hook copied vendored sources with fresh timestamps.

* Production design

- nix/producer-sources.nix separates dependency tools, compiler qualification
  inputs and the complete SDK payload. The dependency tool uses the committed
  verified floor. The compiler platform includes only mandatory LazyMemo.
- priv/build/unit-store.bl is the SDK producer selected by build/produce!.
  It verifies prior units and compares the source inputs their constructors
  actually captured. Compiler and exact runtime identities bound reuse.
- nix/bl-drop.nix exports unit-store; managed SDK jobs freeze and retain a
  predecessor. Inventory sealing and source-free runtime admission stay in
  the existing producer/receiver. There is no executable prototype recipe.
- Native dependency products contain compiled Cargo targets with the selected
  crate's artifacts removed. Real builds always compile the chosen crate.
  Vendored input timestamps are stable; path dependencies and support files
  remain dependency-cache inputs.
- Full application builds can use a verified parent under the same exact SDK.
  Canonical units reuse their captured inputs, full selection prunes removed
  units, and identical requests select the existing product. Force bypasses
  reuse. Contextual World products retain their existing complete producer.
