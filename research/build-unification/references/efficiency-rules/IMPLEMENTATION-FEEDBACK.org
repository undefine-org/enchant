* Membership is independent of sparse presentation columns
E-N reports q-window AND bounded q-page yielding 41 identities beginning with
room types and nil conversation order for a property/order/id query. This is
an observed selected-SDK/read-plan counterexample to that application's intended
membership. It is not a claim about all Datalog or proof of an isolated engine
root cause. The refusal protected hydration; it did not make selection correct.
An index-ready/checkpoint flag alone cannot certify an adapter's query semantics.

The product's dedicated conversation-property facet encodes native membership,
while title/order/search projections describe selected members. Their roles must
not be conflated: missing title/order is neither sufficient proof of nonmembership
nor permission to return another kind. Treat malformed projection data as refusal
or an explicit repair obligation. Retain canonical native eid, actual kind,
property, conversation and ordering validation before hydration. Validate omitted
AND returned membership against an oracle; checking returned rows alone can miss
silently dropped eligible records.

S: [[file:../../priv/lib/datom/query/rank-plan.bl::(defn descriptor][rank-plan/descriptor]] requires exactly one bound scope, same-root scalar
cardinality-one fields and no computed relation/predicates/joins. It embeds schema
evidence. Adding literal kind="conversation" may improve membership but introduce
a second scope and lose this optimization's capability. Query correctness cannot
be weakened to meet an optimizer's admitted shape. Conversely, preserving correct
results by adding a filter does not preserve rank readiness/deep-window cost.
S: [[file:../../priv/lib/datom/query/rank-query.bl::(defn page-result][rank-query/page-result]] separately declines custom budgets on the rank path.
These are existing inspected constraints, not generic pagination properties.

Serious alternatives:
| Design | Advantage | Obligation / cost |
|--------+-----------+-------------------|
| Explicit kind + property predicates over canonical facts | Simple semantic authority, fewer maintained facts | Shape may lose rank eligibility; select an honest bounded plan/refusal, never unbounded fallback |
| Dedicated typed membership facet with scope/order composite (parent approach) | One scope supports efficient selection and separates membership from sparse fields | Transactional maintenance/retractions, source+all-facet completeness, repair/backfill/schema version and canonical parity |
| Broader native multi-scope rank capability | Less app-specific redundant membership, richer queries | Future upstream engineering plus metering/semantics/maintenance qualification; not implemented or proved here |
| Owned derived read product with a closed membership definition | Share selection/enrichment and make readiness explicit | Storage/write amplification, freshness/repair/lifetime and independently qualified implementation |

The API should expose requested semantics and actual admitted capabilities
separately: entity domain, scopes, projection, order/ties, policy, current/historical
view, cursor/window support, count semantics, budget coverage and readiness.
No proposed descriptor should state merely =:indexed true= or =:bounded true=.
Mixed-kind, missing-field, foreign-scope and nil-order cases belong in ordinary
scaffolds/qualification, not only homogeneous synthetic list tests. No semantic
compiler proof follows until actual runtime adapter fidelity is qualified.

* Final v3: owned derived closed inputs, not a cross-render cache
U: the packed 13-key count map and newest-24 ALL-message IDs are maintained in
canonical writer transactions/owner repair. A validated source+all-facet checkpoint
authorizes proven-zero skips. Positive related kinds keep bounded reads and count
parity. Window IDs undergo actual kind/property/conversation/order checks and
canonical hydration; latest-public/current-input pointers remain separately checked.
There is no cross-render cache in this mechanism.

The distinction changes the design model. An optional cache may disappear without
changing semantics; an exact derived facet used to prove a skip must either have
valid complete provenance or cause refusal/reconstruction under a separate bounded
protocol. It cannot turn an unavailable/missing index into empty business data.
The writer transaction/repair owner is responsible for its derivation, not the
screen or a process-local memo cell. That ownership is a logical/storage contract,
not a native authority grant from a map or =version= field.

A count per kind and a fixed message window are a closed read input for specified
operations, not a complete hotel snapshot. "13 keys" bounds the number of kinds,
not the entity populations, bytes of IDs, counts or native hydration work.
"24 IDs" bounds window cardinality, not underlying history/seek work needed to
maintain it, nor arbitrary message size or external proof lookups. The 2 retained
global queries still need their own physical budgets. Zero-heavy fixtures can
make the fast path look excellent while positive kinds remain expensive.

Packing is a representation choice: use a versioned exact key order/type/domain;
missing/truncated keys, unknown kind, negative/overflowed counts and decoding errors
are unsupported, not zero. A map is easier to inspect and extend; a packed vector
can reduce repeated keys/bytes at decoding/version cost. Neither representation
establishes truth. Additions of a fourteenth related kind require a deliberate
schema/derivation/consumer upgrade or explicit unknown, not default empty behavior.

* Negative evidence must prove absence in the right universe
A useful future evidence envelope (proposal, not a shipped API) identifies:
- Authoritative source/view/basis, property/conversation and exact kind universe.
- Derivation/facet schema and implementation identity, provider semantics, source
  and ALL relevant facet checkpoint coverage, repair/generation state.
- Exact count/complete admission assertion, its eligible operation, and current
  policy/time/journal dependencies if the assertion depends on them.
- A current matching capture/entity-map witness for in-read reuse; incomplete,
  stale or unknown status explicitly blocks the skip.

For example, exact raw same-scope count=0 can justify no raw rows of that covered
kind at that basis. A missing count cannot. Positive count requires admitted read
and parity/complete-result validation; an incomplete page of zero returned rows
cannot contradict the count by claiming exact absence. A count can be internally
consistent yet wrong because both read paths used the same defective facet;
compare to independent canonical reconstruction. Signed/trusted data alone does
not prove derivation completeness. Avoid publicly exposing count/window evidence
for internal/revoked data just because the server needs it to check consistency.

Top 24 ALL-message IDs intentionally includes internal, evidence and revoked
messages in the described parent design. Replacing it with top 24 public messages
changes its universe and can conceal evidence relevant to current-input proof.
Conversely, filtering an all-message window is not generally equivalent to the
latest 24 public messages: it may underfill. Keep separately checked latest-public
and current-input pointers, explicit selection semantics and bounded fallback when
additional data is required. Returning 24 IDs and checking their individual fields
alone cannot prove none was omitted or that the top boundary is complete.

U: full canonical coverage can reuse same-DB/same-basis/property/exact-COMPLETE
admission records when the entity-map witness matches. It skips ONLY provably
EMPTY attempt candidate sets. Every input keeps its existing unknown/reviewable
classification, and positive-candidate current/historical proof bodies are unchanged.
This is scoped reuse of an established admission/result, not blanket memoization
or a theorem that no command/effect exists. Zero attempts is not proof that a
judgment is clear or an input is satisfied. A different map witness, partial
admission or historical/current mismatch must refuse this reuse. Its value/cost
benefit does not authorize weakening original proof bodies or bypassing positive
candidate checks. A witness is evidence only under the actual constructor and
scope agreement; a freely assembled receipt cannot mint authority.

* Writer budgets and transaction atomicity
U: whole-world rebuilding message normalization and lazy retraction/index folds
exceeded the 512MiB native lazy-cache budget. Strict folds plus small-record
normalization preserved semantics in the parent's reported repair. E-N records
a lazy-budget failure for an intermediate large fixture; the detailed later repair
is U, not newly executed or independently checked by this review.
S: [[file:../../priv/host/lazy_memo.bl::(defn cache_budget][lazy memo]] defines a default 512MiB off-heap retention admission ceiling.
This is distinct from the optional finite-value cache's 8MiB entry ceiling in
[[file:EXECUTED-FINDINGS.org][the previous update]]. Neither is a general process RSS allowance or evidence
that a pure/eager algorithm meets a transaction work bound.

Strict folding can avoid large deferred graphs, while whole-world eager traversal
can remain unbounded. Normalize changed/small records when equivalence permits;
measure canonical retractions, relation facets and derived updates, not only the
returned transaction. Publication/normalization/repair may dominate even after
readers become cheap. Compiler capture diagnostics should cover command preparation
and writer turns as well as screen callbacks. They cannot prove arbitrary host
allocation bounds from source alone.

U: one 80-record synthetic bulk transaction exceeded the 30s native writer turn.
The fixture now uses ten bounded 12-record transactions. Different workload and
transaction boundaries preclude a controlled performance ratio or claim that
unbounded bulk works. Batching is appropriate only where partial durable progress
is allowed. Ten commits are not one atomic business transition. Each commit must
keep source/facets/checkpoint consistent, handle idempotent retries/reopen, and
make partial fixture readiness explicit. A user command requiring all-or-none
cannot be silently split to satisfy a turn budget.

Alternatives: limit batch input/fan-out and reject before admission; construct
bounded deltas rather than whole-world rebuild; resumable import with durable
checkpoints and unpublished staging then an atomic qualified switch; or a
separately designed multi-step domain workflow/compensation. Each has distinct
resource, visibility and atomicity obligations. Timeout after acceptance is an
uncertain observation until original receipt/status lookup; it is not safe replay.
Bounded record count alone is insufficient with large records/relations/history.

* Data, code, catalogue identity: do not equate opaque tokens
U: normalized hotel-attribute evidence with FRESH stored-provider proof avoids
false conflicts from opaque catalogue tokens. Do not interpret this as deleting
provider/code dependencies. A catalogue token may change due to unrelated registry
activity, causing conservative misses/refusals without changing relevant semantics.
The safe refinement narrows evidence to the actual covered attributes while
freshly proving absence/identity of provider shadows at use. Unknown providers
still refuse; data equality alone cannot certify computed semantics.

S: [[file:../../priv/lib/datom/query/read-plan.bl::(defn attributes][read-plan/attributes]] discovers dependencies of a closed fragment, including
negative/empty clauses, and declines unsupported predicates/computed providers.
[[file:../../priv/lib/datom/cache-validity.bl::(defn read-stamp][cache-validity]] and [[file:../../priv/lib/datom/query/relation.bl::(defn stored-attributes-stamp][stored-attributes-stamp]] provide conservative existing seams;
they do not automatically certify parent facets or arbitrary normalized proofs.

Separate exact data-view/basis identity, normalized relevant schema/attribute
meaning, actual emitted derivation/helper code identity and current provider
registry/declaration semantics. Broad tokens are safe but may be imprecise;
normalized tokens need a justified equivalence relation and complete dependencies.
Do not use application-defined equality, a constant generation number, a hash of
selected output rows or a stale stored-provider proof as a substitute. Namespace/
SDK/policy/source-free agreement and races around evidence capture remain explicit
obligations. No new canonical identity API is implemented in Beam Lisp here.

* Resource-free renderer DTOs
U's final cleanup removes unused DB/worker handles, plans and capabilities from
Guests DTO while keeping scalar independent journal bases. Its small rerun is
pending. It is a stronger modular boundary and potential retention reduction,
not a measured new speedup or proof of result equivalence.

A proposed renderer DTO is eager bounded presentation data, result/completeness
states, explicit time/locale, stable component/attempt references and safe scalar
provenance. It excludes executable closures, live DB/store handles, workers/native
registrations, command/provider capabilities and plans with embedded authority.
Command adapters/owned read composition retain the resources they need outside
screens. Scalar journal bases do not invent one atomic distributed revision.

Resource-free is separate from authorized-to-disclose: plain data can still contain
private evidence, secret strings or overly broad history. Eager first-order is
separate from small/finite-work. Removing unused keys is useful only after proving
no consumer requires them, including temporal callbacks, current/historical proof,
controller payloads and fallback/error paths. Static DTO shape checking can help
inside its supported type fragment; runtime bounded realization/size checks and
consumer regressions still matter. Do not turn a broad DTO into 13 redundant
handwritten type/effect/ownership schemas.

* Holistic API choice after implementation feedback
A (explicit values/functions) continues to show immediate value: the parent repaired
membership, sparse enrichment, folds and DTOs with existing APIs. B (declarative
features) should link semantic read domains, actual plan capabilities, owned
resources and evidence references, rather than duplicate canonical policy/schema.
C (checked roles/evidence) can demand covered DTO/dependency/capture/lifecycle
properties and reject unknown; runtime query fidelity and native adapter conformance
still require qualification. D (owned derived read products) is now more compelling
for sparse count/window enrichment, but its transactional completeness/maintenance
cost cannot be hidden behind optional-cache terminology.

Do not generalize a hotel-specific 13-kind/24-message schema into a language DSL.
First specify a small derived-input contract with typed membership, explicit
scope/universe, completeness/checkpoint, budget/readiness and source/code/provider
identities. Keep zero-skip eligibility a checked operation with narrow semantics;
positive reads keep canonical proof. Test whether an independent non-hotel consumer
needs the same abstraction before public constructor design. A compiler-produced
inventory can link these contracts without becoming a second authorization,
query engine, effect system, proof ledger or workflow authority.
