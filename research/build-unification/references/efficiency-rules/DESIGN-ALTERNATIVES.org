#+title: Competing holistic application API designs
#+date: 2026-10-26
#+status: Design alternatives; all proposed namespaces and contracts below are hypothetical

* Decision and criteria
The best near-term candidate is ordinary explicit composition values with a
small declarative feature adapter and optional compiler-checked profiles. This
is a conditional recommendation, not a claim that combining every proposal is
free. Alternative A must remain independently useful; B earns adoption only
when two consumers remove actual duplicate wiring; C earns strict defaults only
when its closure and native-leaf coverage qualify. See [[file:CURRENT-MODEL.org][current source behavior]].

Compare the SAME multi-tenant notes application: list 40 notes by title, tenant
membership revocable during a session, title search, detail and edit, HTTP SSR
plus Live, optional export worker and private offline draft. A correct design
must handle unsupported search, refused hydration, response loss and reload.
A pleasant route example that leaves those unspecified is not a serious option.

| Criterion | A: explicit functions and values | B: declarative feature/capability composition | C: checked roles and evidence |
|-----------+----------------------------------+---------------------------------------------+-------------------------------|
| Author unit | Ordinary module plus app map | Feature value assembled from smaller values | Declared entry role + exact checked closure |
| State authority | Datom and existing command journal | Same; description references those owners | Same; proof artifacts cannot become a second store |
| Main simplification | Standard result/context/attempt conventions | Route/read/command/lifecycle adapters derived once | Violations/unknown dependencies block strict publication |
| Runtime enforcement | Native query/auth/lifecycle leaves | Same leaves, validated constructors | Same leaves plus qualified execution admission |
| Static guarantee | Optional diagnostics | Descriptor consistency only unless checked | Scoped proof relative to covered IR/contracts |
| Bootstrap/cost | Lowest; source compatible | Moderate builder/composition/schema work | Highest closure, primitives, invalidation, SDK work |
| Dynamic application code | Fully supported with explicit boundary | Opaque callbacks easy to embed, weaken checks | Unknown or needs a qualified contract |
| Portability | Existing targets independently tested | Adapters can target HTTP/MCP/Live | Checked placement still needs backend equivalence |
| Migration | Per read or form | Per feature; preserve existing app factory | Per entry; no all-or-nothing repo conversion |
| Principal failure | Convention drifts | Manifest becomes an inert annotation inventory | Excessive unknown/refusal or false trust from weak model |

No scored total: custody, non-disclosure and honest incomplete outcomes are
mandatory gates, not weights that better ergonomics can outweigh.

* A — extend current APIs and ordinary functions minimally
** What an author writes
The following syntax deliberately uses existing =datom/q-page= at its existing
boundary; =notes.scope=, =notes.read= and =notes.commands= are application helpers.
The =hydrate-selected!= behavior and standardized attempt envelope would require
new reusable support. Nothing here is executable code delivered by this research.

#+begin_src clojure
(defn list-read [read-context params]
  (let [{:keys [database policy now]} read-context
        scoped (auth/query-context database policy)
        p (datom/q-page note-query scoped
            {:order-by ['?title :asc] :limit 40
             :budget {:rows 1200 :seeks 800 :bytes 1048576}
             :authorization (:freshness read-context)
             :after (:after params)} (:tenant params))]
    (case (:status p)
      :exact (notes.read/hydrate-selected! read-context p [:note/title])
      :incomplete {:status :incomplete :continuation (:after p)}
      :refused {:status :refused :reason (:reason p)})))

(defn notes-screen [{:keys [worlds]}]
  (notes.ui/list (:notes worlds)))

(defn app [owned]
  {:routes [["/notes" notes-screen] ["/notes/:id" detail-screen]]
   :principal (:principal owned)
   :shared-conn (:command-store owned)
   :worlds (fn [me params] (notes.read/route-data owned me params))
   :observe (fn [_] [(:command-store owned)])
   :intents {:save (:save-note owned)}
   :clock (:clock owned) :deadline notes.read/next-deadline})
#+end_src

** Holistic semantics
Composition owns store, workers, clock and shutdown. Read context captures an
immutable DB, principal, policy freshness and explicit time; routes call ordinary
read functions. Screens get finite values. Commands validate against current
state under the existing writer/journal and return receipts. Forms render a
preexisting attempt value, not a fresh UUID. HTTP and Live share command handlers
through explicit adapters. Deployment packages the existing module/resource
closure. Tooling can use resolved graph checks without changing author syntax.

Small CRUD needs two functions and an app map. Multi-tenant search needs a real
search plan and scoped hydration; convention cannot make an arbitrary query
bounded. Hotel effects use the existing operation journal and provider adapter.
Long jobs use native queues and durable progress, not an HTTP callback kept alive.
Private offline state adds a specific browser draft adapter, not server session
state mislabeled offline. All five remain expressible without a feature macro.

** Strength and cost
A avoids an extra metaprogramming phase and keeps source/type error positions
ordinary. A non-Live consumer can call reads/commands directly. Existing tests
and deployment do not need to ingest a feature description. It provides the
fastest falsification of whether the proposed common vocabulary is actually
sufficient: duplicated glue stays visible rather than hidden in generators.

Its weakness is drift: routes, HTTP access, socket access, command adapters,
presentation hints and lifecycle can still disagree. Constructor validation
can catch missing fields but cannot see arbitrary render helper IO. Strict
query/hydration/native capabilities must still be real leaves; a record named
=:scope= is not one. Shared helpers may turn into another undocumented framework.
Use canonical adapters only where duplicated code proves the need.

** Soundness and escape
A permits any code by default, so its unconditional guarantee is only what the
called native operations enforce. Diagnostic roles are useful evidence, never
proof of the whole app. An opaque callback is labeled unverified; a bulk export
is a separately admitted worker with its own cap. An unsupported page never
falls back to =q -> filter/sort -> take=. This design is still useful before
any stronger static checker lands.

* B — feature descriptions with capability-oriented composition
** What an author writes
All =feature/=, =read/= and =operation/= names are proposed constructors,
not current public APIs. These are immutable values with references to ordinary
functions, not strings that a generator resolves later from ambient Env.

#+begin_src clojure
(def notes
  (feature/describe
    {:id :notes
     :requires {:read :notes-reader :commands :notes-writer}
     :routes [{:path "/notes" :access member-policy
               :read notes-page :screen notes-list}
              {:path "/notes/:id" :access member-policy
               :read note-detail :screen note-editor}]
     :operations {:save save-note}
     :presentation {:save {:fields save-field-hints}}
     :drafts {:edit {:owner :browser :schema edit-draft-v2}}
     :deadlines note-visible-deadline}))

(def notes-page
  (read/describe
    {:source :notes-reader :select note-query
     :order ['?title :asc] :limit 40
     :scope member-policy :shape note-list-shape
     :budget {:rows 1200 :seeks 800 :bytes 1048576}
     :search {:strategy :prefix-index :max-chars 120}
     :count :omitted}))

(def app-description
  (application/compose
    {:features [notes exports]
     :bindings {:notes-reader notes-read-binding
                :notes-writer save-command-binding}
     :resources owned-resource-plan}))
#+end_src

** What the description really means
Describe requires/exports, data shape and reference identities. It contains no
DB handles, principal values, active ownership tokens, solver sessions or secrets.
Composition resolves requirements at startup to actual owned/borrowed capabilities;
runtime separately authenticates them. Validation catches missing providers,
duplicate feature/route IDs, ambiguous precedence, absent command bindings,
unsupported version combinations and attempts to send authority to clients.

A compiler/adaptor derives routes and transport allowlists from one route entry;
the one policy reference is reused by HTTP SSR, socket navigation and command
admission as appropriate. These operations have different outcomes: HTTP 403/404,
socket refusal and command refusal cannot all become a screen returning 200.
Read visibility and write eligibility may intentionally be different predicates;
one vocabulary must permit that difference without copying conditions.

Operation schema owns input normalization; field hints add labels/order/widgets
without redefining types or business validation. Storage schema is not necessarily
the command schema: a =rename-note= command need not expose internal tenant ID,
provider receipt or audit columns. One source per semantic concern is the goal,
not one giant schema forced onto unrelated concerns.

An export feature declares a job entry and reads, but its owner still is a queue.
A hotel feature references durable operation state, consent and effect adapter;
the description cannot make remote calls transactional. Offline drafts declare
ownership, schema version and explicit merge/expiry rules. Generated scaffolds
can demonstrate all these conventions without relying on inference.

** Strength and cost
B directly removes repeated route/schema/transport glue and can generate useful
MCP catalogues, tests of route coverage, asset/resource closure lists and startup
readiness stages. Modules publish small descriptions and compose them: there is
no required global whole-app registry before one feature can be analyzed.

The cost is a versioned descriptor vocabulary, adapter conformance and reference
resolution rules. A description can become annotation theatre: =:pure true=,
=:scoped true= and =:cost :bounded= prove nothing. Avoid those fields; store a
requested profile or enforceable plan instead. It can become a monolith when
forms, job internals, provider protocols and queries all need bespoke language
extensions. Keep adapters and leaf descriptions separately versioned; a feature
only links them. Compilation must not instantiate stores or start workers to
learn what routes exist.

** Soundness and escape
B establishes structural consistency, not arbitrary callback correctness. Native
admitted plans/capabilities enforce authority/budgets; C-style analysis is an
optional consumer of the same description. Explicit escape =:opaque read-hook=
means unsupported static checks, advertised operational cap and required runtime
evidence. It cannot satisfy a strict render/read obligation merely by having a
well-shaped descriptor. There must be an inspectable expansion showing which
handwritten function and generated adapter ran.

* C — compiler-checked roles and current evidence as publication inputs
** What an author writes
All role declarations below are hypothetical. Metadata is a request, not evidence.
The compiler must check actual expanded/resolved bodies and dependencies.

#+begin_src clojure
(defn ^{:application/role :render} notes-list [finite-model]
  (note-table finite-model))

(defn ^{:application/role :read
        :application/requires [:notes-reader]
        :application/budget {:rows 1200 :seeks 800 :bytes 1048576}}
  notes-page [read-context params]
  (read/page read-context note-plan params))

(defn ^{:application/role :command
        :application/schema save-input
        :application/effects [:notes-write]}
  save-note [command-context attempt]
  (notes.domain/save! command-context attempt))

(def checked-notes
  (application/check-description notes {:profile :bounded-interactive}))
#+end_src

Publication binds entry -> contextual expanded bodies -> all supported immediate
and latent dependencies -> primitive models -> obligations -> emitted code IDs.
Complete current evidence is checked once at publication; invocation verifies
actual selected code/context/custody and enforces native budgets/authorization.
No page invocation starts the compiler or solver.

** Roles must be a property product, not a new effect ladder
=:render= requires eager finite input/output, input-only determinism over explicit
locale/time, no ambient effects, and covered callbacks; CPU/allocations/output
need independent budgets. =:read= permits declared immutable data access and
admitted finite work; it can legitimately return incomplete/refused. =:command=
permits precisely owned state transitions and journaled effects, but the role
does not prove domain validity. =:compose= can acquire resources under ownership
protocols. =:controller= belongs to the browser target and is checked against its
own DOM lifecycle adapter. Model these as checked requirements of existing
summaries, types, suspension, ownership and native leaves, not a second lattice.

Read-only is not deterministic; termination is not a useful cost ceiling; stable
IDs are not command identity; checked dependencies are not permission to execute.
Each distinction must survive in diagnostics and release policy.

** Strength and cost
C can reject hidden render -> owner/process paths, stale callee evidence,
missing strict plan budgets and known effectful callback escapes. It gives
agents useful reasons/witnesses instead of repeating style rules. It can connect
performance/authority requirements to the actual package rather than prose.

C is the most expensive alternative. Current tag checking is not a refined
record/capability type system. Contextual graph, summaries and emitted graph do
not already form a complete identity-preserving role pipeline. Macro/host/lazy/
higher-order coverage, schemas, initializers, callbacks and dynamically selected
plugins require qualification. A permissive =any= becomes a hole; fail-closed
unknowns may make most existing code inadmissible. Unmeasured developer cost can
undo the benefit through repeated expansion and broad solver queues.

** Soundness and escape
A strict entry admits only obligations with accepted modalities AND complete
applicable coverage. Unknown, unchecked, stale, sampled and error stay distinct.
Unsupported dynamic code can run as an explicitly unverified integration behind
a native constrained capability, but cannot inherit the render-role theorem.
The authority boundary remains native and qualified, independent of annotations.
No extension should claim to sandbox arbitrary host interop in the same VM.

* A fourth contender: materialized data products and explicit workflow graphs
This alternative deserves consideration rather than hiding it inside B. Authors
write authoritative events/commands, maintained query products and durable
workflow transitions. Routes and screens become consumers of named data products;
all effects live in workflow nodes with durable identities. It resembles a
CQRS/dataflow application architecture, expressed through existing Datom/native
queue mechanisms instead of a universal page DSL.

#+begin_src clojure
(def list-product
  (product/describe {:source :notes :derive note-membership
                     :order [:tenant :title :id] :through :source-basis
                     :scope member-policy :budget product-maintenance-budget}))
(def export-flow
  (workflow/describe {:states [:queued :reading :writing :unknown :done]
                      :transitions export-transitions
                      :effects {:write export-provider-contract}}))
#+end_src

It is strong for shared costly aggregates, search indexes and recoverable jobs;
several consumers reuse an explicit maintained projection. It is weaker as the
ordinary tiny CRUD model: backfill, causal completeness, write amplification,
recovery, lag and retention become mandatory concerns. It creates a second state
machine when existing native journals already own a workflow. It does not solve
current permission revocation just because product rows carry a tenant column.
Choose it per measured read/maintenance economics, not for every feature.
Require =through= coverage, recovery semantics and separate maintenance admission.

* Challenge the starting assumptions
1. "One compiler description should drive everything" is too strong. One linked
   inventory can remove duplicate IDs/references, but domain policy, UI hints,
   storage schema, ownership receipts and proof claims have different authorities.
   A flat universal descriptor would need to reimplement them all.
2. "Strict roles first" may front-load a compiler project before cheap fixes.
   Qualified native read leaves and ordinary values improve A immediately.
   C should follow supported vertical slices, without blocking parent delivery.
3. "Every screen needs bounded paging" excludes a legitimate small single-record
   form. Budget data access directly; a detail read needs scoped finite hydration,
   not an artificial collection/cursor abstraction.
4. "An exact count belongs on every list" can force growing work or maintained
   state. Omit it, use a justified estimate/bound, or admit an independent count
   operation. Approximate values must be labeled and may still disclose scope.
5. "Derived views solve invalidation" is false without dependency completeness,
   authorization freshness and clock transitions. The simplest safe default is
   cheap projections with complete Live subscriptions.
6. "No reads should acquire anything" conflicts with opportunistic rank workers.
   Either separate preparation from invocation in a strict profile, or explicitly
   admit maintenance as a distinct owned effect with independent limits.
7. "Everything should be a socket intent" ignores uploads, OAuth, HTTP callbacks,
   CSRF, content limits and provider boundaries. Share an operation envelope and
   domain handler; preserve transport-specific admission.
8. "Git revision is enough for the ledger" fails with dirty source, mutable
   dependencies, schema/policy changes and SDK artifacts. Conversely hashing
   entire corpora at every edit loses incremental economics. Bind exact dependency
   identities once, then invalidate affected obligations.
9. "An offline draft is portable because render is pure" confuses computation
   placement with data placement/authority. Pure tenant data can still be secret.
   A client bundle must pass explicit disclosure and resource packaging checks.
10. "Solvers can fill all remaining gaps" hides real backend/provider/DOM semantics.
    Use finite models to expose errors; maintain a trusted-leaf qualification list.

* Concrete selection procedure
First build a disposable vertical design prototype after this research (not
implemented here): A tiny CRUD and an independent tenant catalogue, each with
HTTP SSR, Live edit and one deliberate unsupported read. Measure handwritten
boilerplate, generated code, closure/unknown counts and unchanged/edit analysis
cost for A and B. Run the same negative fixtures under C. Compare data-product
maintenance against direct page reads on high-churn/low-read and low-churn/high-read
loads; do not select materialization only from read latency.

Choose A if B saves little glue or adds many descriptor-only concepts. Choose B
for linking and adapters only if it removes route/schema authority duplication
without hiding refusals. Choose C per strict feature entry only when the checked
closure meaningfully covers its real dependencies and tool cost is acceptable.
Defer automatic minimal invalidation and universal workflow inference even if
all three vertical slices succeed. Their proof obligations are independent.
