* Consequences for the holistic API research
These are design inferences, not implemented Beam Lisp features:

- A replayable Source classification and a finite dependency graph are
  necessary but insufficient evidence of native artifact constructibility.
  An application build plan should expose constructor support separately and
  run a bounded component preflight before expensive substrate/legacy work.
- Cross-phase SDK macro dependencies belong in the preparation model. A source
  world below its cardinality ceiling can still contain an unsupported staging
  cycle. Silently increasing budgets or replacing the constructor guard would
  not demonstrate correct phase separation.
- A legitimate product fallback must name the affected units and retain their
  actual Source. An immutable source-retaining deployment, an ordinary verified
  artifact receiver, and a compiler-free runtime are distinct qualification
  targets. None should borrow another's success receipt.
- Startup admission needs an explicit wall-clock/resource contract before the
  first usable MCP response. A bounded Source reader or successful page render
  does not certify that protocol initialization is ready.

* Executed constraint: numeric-window syntax is not a guaranteed rank read
On the retained SDK, an explicit =:budget= makes =q-window= decline its rank
path and use the ordinary bounded page path. This is an intentional accounting
boundary: rank metadata does not yet account for every byte and seek in the
caller's custom units. Removing that option changes the envelope: rank nodes
have 4092 reads and 7,864,320 bytes, plus header/frontier work; ordinary fallback
has default 4096 rows/seeks and 8 MiB. These are not the reader's previous custom
1104-row/844-seek envelope for a 65-record request.

Source inspection establishes two constraints, not an empirical claim of a
specific durable header refusal. Cold =q-window= calls =query.page/page=;
construction demand is paid only by ordinary engine execution through
=rank-demand/record-scan!=, which that bounded page path does not call. Repeating
only the numeric-window path therefore does not itself pay construction demand.
In addition, =rank-build/MAX-INDEXES= is 4 per store, while the index identity
includes the scope value. Forty conversations times summary/judgment means 80
distinct candidate index identities; automatic maintained rank cannot keep all
80 live under that contract. Eligible syntax may project all three variables
including the entity; a two-column restriction was not the cause. The demand
cache was disposable and disappeared with the profile VM, so its exact values
were not recovered after shutdown. Declaration of a composite schema attribute
alone does not prove that this separate maintained-rank mechanism will activate.

A future query API should expose the selected execution contract, budget units,
construction prerequisites and maintenance capacity as reviewable values. A
structural query/read plan should distinguish a guaranteed bounded seek from
an opportunistic rank accelerator and its ordinary fallback. A product-side
sealed bounded identity projection is a viable alternative to many independent
per-conversation queries, but requires atomic writer evidence, exact membership
and canonical scope checks; it is not permission to trust a packed facet alone.
These constraints do not assert that a new API or schema extension has shipped.
