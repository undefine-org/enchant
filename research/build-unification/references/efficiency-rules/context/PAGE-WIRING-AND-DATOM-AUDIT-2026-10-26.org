#+title: Backdesk page wiring and Datom audit
#+date: 2026-10-26

* Conclusion and evidence

Datom usage is a substantial improvement opportunity. The present Guests page
limits displayed rows after an unrestricted candidate query and in-memory
filter/sort. Adding more indexes alone does not bound this work. Live already
provides sockets, navigation, reconnect, ordered event coalescing and keyed
patches; Backdesk should give that machinery smaller, deterministic projections.

An isolated probe exercised the actual =desk/find-guests= helper against two
synthetic in-memory Datom connections with indexed property/kind attributes.
Its underlying ordinary query was profiled separately with =datom.profile=:

| Conversations | Displayed rows | Query result rows | Profiled store rows | Range operations | Page operations |
|---------------+----------------+-------------------+---------------------+------------------+-----------------|
|           100 |             40 |               100 |                 300 |                3 |               0 |
|          1000 |             40 |              1000 |                3000 |                3 |               0 |

Both runs used indexes, with zero =:scan= operations. Three indexed ranges can
still return a growing amount of data. The small timing samples have different
warmup costs and do not establish a latency-growth ratio or live-store timings.

A second actual runtime probe formatted40 timestamps through =hotel.time/label=.
It took400ms on first use and35ms on the repeat. Each label invokes system
=date=. This is avoidable render work, but does not explain the earlier
four-minute application-readiness timeout.

The existing JavaScript lifecycle check fails with =TypeError: form.matches is
not a function=: its fake form lacks an API used by the current adapter.
Real browser forms have this API. This is a stale harness, not a demonstrated
production DOM defect.

[[file:../evidence/page-wiring-audit-2026-10-26.json][Probe drivers, measurements, source hashes and validation limits]]. No application
implementation changed. The retained SDK was used; this does not qualify a new
runtime release. Source findings below are distinguished from measured costs.

* Efficient wiring with the existing modules

The useful flow is:

#+begin_example
authenticated request / socket identity
  -> immutable hotel basis + explicitly captured execution-journal bases
  -> authorized query for page identities
  -> bounded batch hydration + route read model
  -> pure screen built from reusable Hiccup / Loom components
  -> live.app routing -> live.socket realization/diff -> live/client.js patch

gesture -> one existing typed command boundary -> durable Datom transaction
        -> native commit notification -> next projection
#+end_example

- =live.app= supplies route matching, SSR, principal capture, worlds, observed
  connections and sessions. Use distinct screen functions in its route table.
- =live.socket= owns ordered events, local assigns, intents, detach/reattach,
  realization and keyed diffs. Keep authenticated identity outside editable locals.
- =loom.ui= and =loom.box= provide accessible Hiccup components and layout;
  =loom.token= supplies the shared theme and render-local stylesheet collection.
- =loom.form= accepts Datom attribute specs, records or explicit field specs.
  Backdesk's JSON procedure schemas need a deliberate presentation adapter;
  replacing them with a second command schema would create drift.
- =loom.surface= targets desktop/mobile WebViews and currently swaps full HTML.
  It is not the replacement for this application's Live web transport.
- =auth/query-context= can apply policy to ordinary queries. Raw =entity=/=pull=
  still need an access-aware path; a query handle alone does not guard those APIs.
- =datom/q-page= provides admitted ordered, bounded plans; =q-window= supports
  numeric windows subject to its admission/readiness rules. Handle refused and
  incomplete results explicitly. Current arbitrary search and active membership
  are not automatically admitted merely by changing the function name.
- =live.measure=, =datom/explain= and =datom.profile= provide phase, plan and
  actual-row evidence. Use all three before attributing a slow page to the engine.

Existing strengths to preserve: property-world memoization by immutable basis,
native scoped snapshot reads outside the command owner on normal Live pages,
eager realization before diffing, keyed conversation-table rows, no adapter
revision polling, mounted-browser disclosure receipts and original command
basis/idempotency fences.

* Prioritized improvement inventory

P1 means first implementation batch; P2 follows once read costs are bounded;
P3 is consolidation. These priorities express expected value, not measured
percentages of total startup time.

** 1. P1 — Replace whole-hotel page inputs with feature read models
=reception.web/app-value :worlds= ignores params and returns
=store/view-snapshot= of the entire property. =native-world/property-world=
memoizes hydration within a basis, which helps repeat reads, but a new hotel
basis still invalidates that broad derivation. Start with Guests and conversation
detail: select authorized IDs and hydrate only their displayed fields. Guest
views should receive conversation/disclosure data rather than the entire hotel
world. This is excessive server-side context, not a demonstrated browser leak.
Sources: [[file:../src/reception/web.bl::(defn app-value][app-value]],
[[file:../src/reception/store.bl::(defn view-snapshot][view-snapshot]],
[[file:../src/booking/native_world.bl::(defn property-world][property-world]].

** 2. P1 — Stop rebuilding a second index in every render
=render-tree= calls =d/indexed= unconditionally. That function folds all entity
records into kind/field buckets; the index is accepted only while a physical
heap-sharing check succeeds. Current code correctly rebuilds after scoping,
but still pays for the rebuild. Native queries and small read models remove the
need for this render index. During migration, retain a valid local index rather
than assuming a transported one is usable. Do not replace identity checking
with a digest that silently trusts stale data.
Sources: [[file:../src/reception/web.bl::(defn render-tree][render-tree]],
[[file:../src/booking/domain.bl::(defn indexed][domain index]].

** 3. P1 — Perform Guests pagination in the read plan
=find-guests= queries all conversation IDs, maps them into records, filters,
sorts, counts and only then takes40. The probe confirms candidate work grows
with the whole result. Define an indexed stable order with a tie-breaker and
use an admitted bounded page/window. Preserve authorization before page
selection. Exact total counts should have a separate, explicit cost.
Source: [[file:../src/reception/procedures/desk.bl.org::(defn find-guests][find-guests]].

** 4. P1 — Give active membership and search explicit bounded plans
The default active list scans the world's entities through =active-conversations=.
Search groups reservations and constructs searchable strings before paging.
These are independent requirements from alphabetical paging. Query typed facts
or maintain a causally updated, purely derived membership/search projection;
preserve activity expiry, retired/synthetic visibility and reservation reference
semantics. A growing full scan hidden behind40 rendered rows is not bounded.
Source: [[file:../src/reception/procedures/desk.bl.org][desk projections]].

** 5. P1 — Batch row enrichment for the selected conversation IDs
=conversations= folds every hotel message for latest-message data, then derives
canonical context, returning-guest links, summary freshness, judgment and
processing state per row. Compute these as a page read model, sharing repeated
derivations and batching indexed conversation reads. The current shared fold
already avoids one previous per-row scan; the next step is narrowing its input.
Sources: [[file:../src/reception/ui/screens.bl::(defn conversations][conversation rows]],
[[file:../src/reception/procedures/desk.bl.org::(defn linked-guests][identity links]].

** 6. P1 — Make Today aggregates independent of full rendered collections
=projection/dashboard= derives active membership, attention, judgments,
reservations, failed/stalled work, delivery, connections and coverage across
broad collections. It also evaluates =attention/property-world= for a discarded
result; verify its intended purpose before removing that call. Build indexed
aggregate/read queries and bounded sections, sharing common inputs once per
basis. Preserve unknown versus clear and canonical attention semantics.
Source: [[file:../src/reception/projection.bl::(defn dashboard][dashboard]].

** 7. P1 — Bound the conversation timeline and related history
=projection/conversation= filters whole kind collections for each relation and
sorts every message. Query by conversation and use a bounded timeline with
explicit older-history loading. Offers, stays, work and retrievals can be
separate read sections. Preserve event sequence/timestamp/ID ordering and
audience filtering before page admission.
Source: [[file:../src/reception/projection.bl::(defn conversation][conversation projection]].

** 8. P1 — Reuse insight freshness calculations within a read
=insights/judgment= recalculates a fingerprint; row rendering also checks
summary freshness, and Today computes judgments separately. The fingerprint
builds/sorts conversation inputs and configured categories. Derive freshness
once per conversation/read context and share it. Any longer-lived memo must
include the actual immutable inputs and configuration; never display a stale
judgment merely because the conversation ID stayed the same.
Sources: [[file:../src/reception/insights.bl::(defn basis][insight basis]],
[[file:../src/reception/ui/screens.bl::(defn conversations][row enrichment]].

** 9. P1 — Remove owner calls and capability acquisition from rendering
Normal Live snapshots already avoid the writer, but =screen-tree= still calls
=instagram/data=, =meta/management-data= and =communication/open!=. Those paths
call =store/read!= or =store/custom!=, and signing status can repeat that per
connection. Render latency can therefore wait behind unrelated commands, and
sections can read different hotel bases. Capture public read capabilities at
composition, prepare route data from one hotel basis, and pass values to views.
Independent journal bases should remain explicitly independent.
Sources: [[file:../src/reception/web.bl::(defn screen-tree][screen-tree]],
[[file:../src/reception/instagram.bl::(defn data][Instagram data]],
[[file:../src/reception/meta.bl::(defn management-data][Meta management]].

** 10. P1 — Make row authorization part of the read API
Current property-world filtering is valuable; replace it with equally explicit
query-level property/conversation guards when narrowing reads. Centralize staff
eligibility and guest disclosure scope, with checked hydration after ID selection.
Do not distribute copies of role/property conditions among every screen, or
assume =auth/query-context= automatically protects raw pulls.
Sources: [[file:../src/reception/web.bl::(defn app-value][world authorization]],
[[file:../src/reception/ui/guest.bl.org][guest projection]].

** 11. P2 — Reduce invalidation fan-out without breaking Live's contract
Every socket observes the hotel connection and several execution journals,
regardless of its current route. A commit can cause a broad projection even
when its resulting screen is unchanged. First make projections cheap and use
compact =:listen {:payload :basis}= notifications where appropriate. Native
Live rejects manual =:attrs= filters: do not add them or omit the mandatory
shared write-world subscription. Stronger scoped invalidation needs a proved
derived read-world design or a supported framework seam, not a guessed filter.
Sources: [[file:../src/reception/web.bl::   :observe][observed connections]],
=live.socket/listen-options= and =live.app/app-socket=.

** 12. P2 — Make observed journal lifetimes explicit
=:observe= reads the current executor atoms when the socket starts; the framework
installs those subscriptions at initialization. Establish how socket lifetime
relates to journals acquired/replaced later, and test recovery. Publish resource
availability through the owned application lifetime rather than relying on a
render calling =open!= to discover it. This is a lifecycle risk to verify,
not a reproduced missed-update failure.
Sources: [[file:../src/reception/web.bl::(defn app-value][app-value]],
[[file:../src/reception/application.bl][application composition]].

** 13. P2 — Keep temporal deadline calculation cheap
The current Live implementation resolves =:worlds= again when rearming a
configured deadline, including after event handlers whose render is coalesced.
Backdesk installs a deadline callback for every route, while most return nil.
Keep its read context lightweight and deadline queries narrow; profile this
separately. Reusing an exact render context would require an explicit framework
contract rather than an application process-dictionary shortcut.
Sources: =live.app/temporal-context=, =project-with-time!=,
[[file:../src/reception/temporal.bl][Backdesk deadlines]].

** 14. P1 — Add deadlines for visible Today/guest time transitions
=next-deadline= handles Instagram and uploads only. Today also has processing
stall thresholds and connection-verification freshness; activity has a recent
message window. These can change without a hotel transaction. Add route-specific
next-deadline readers and virtual-clock browser checks. The store's reminder
scheduler does not publish a transaction for every clock advance, so it cannot
serve as a general view clock. Avoid a global refresh interval.
Sources: [[file:../src/reception/temporal.bl][next-deadline]],
[[file:../src/reception/store.bl::(defn tick!][store clock]],
[[file:../src/reception/projection.bl][time-sensitive dashboard]].

** 15. P1 — Remove process launches from timestamp rendering
=hotel.time/label= invokes system =date= for every modern timestamp. Format in
process using a qualified timezone-aware library, or batch/cache exact immutable
formatting inputs. Preserve Africa/Casablanca tzdata and Ramadan transitions;
a fixed UTC offset is not equivalent. Include date and clock helpers used by
the owner's deadline scheduling in the same consolidation.
Sources: [[file:../src/hotel/time.bl][hotel time]],
[[file:../src/reception/ui/parts.bl::(defn time-label][time-label]].

** 16. P1 — Allocate command IDs at form/attempt lifetime boundaries
=forms/sheet=, =post-button=, inline date editors and signing forms mint random
IDs while rendering. Equal read state therefore produces changed hidden fields,
creating patches and requiring browser restoration of the original identity.
Allocate once for the form/attempt, retain its original basis and payload, and
renew after a confirmed completion or explicit fresh attempt. Keep uncertain
outcomes attached to their original idempotency identity.
Sources: [[file:../src/reception/ui/forms.bl][form rendering]],
[[file:../src/reception/ui/screens.bl::(defn date-editor][date editor]],
[[file:../src/reception/ui/webhook_signing.bl][signing form]].

** 17. P1 — Give dynamic rows stable Live keys
Conversation table rows already have keys. Message articles use =:data-message=
but lack =:key=; stay cards and several mapped sections also lack keys. A DOM
data attribute is not Live reconciliation identity. Use entity IDs plus any
necessary component-role namespace. Run the existing =live.lint= checker and
test insertion/reordering with focused controls rather than just final HTML.
Source: [[file:../src/reception/ui/screens.bl][messages, stays and mapped sections]].

** 18. P1 — Namespace field and form identities
=forms/field= uses =input-<field-name>=. Multiple inline date forms can render
the same arrival/departure IDs. Browser draft storage prefers field ID, while
form identity includes its ordinal position in =document.forms=. This creates
collision and reorder risks. Use stable component/form/record identity for
DOM IDs, label targets, keys and draft paths. Keep command identity separate
from visual identity.
Sources: [[file:../src/reception/ui/forms.bl::(defn field][field IDs]],
[[file:../src/reception/ui/interactions.bl.org][formKey, key and drafts]].

** 19. P2 — Choose a single owner for each kind of draft
The adapter keeps DOM drafts and original bases, while typed field changes and
PMS selection also live in socket locals. Live already has ordered input/ack
handling for controlled fields. Use locals or =:session-for= private state for
appropriate non-secret drafts, and retain browser-only handling for files and
passwords. Preserve original command bases intentionally; removing all draft
restoration at once would lose existing behavior.
Sources: [[file:../src/reception/ui/interactions.bl.org][draft adapter]],
=live.socket/resolve-intent-payload=, =live/client.js=.

** 20. P2 — Stop doing document-wide maintenance for every patch
=update= scans all inputs and forms, restores twice, scans controller nodes,
checks focus/dialog state and runs delivery logic after each patch. Combined
with global basis attributes and random IDs, small data changes trigger broad
browser work. Use stable component roots, targeted patch lifecycle handling
and native input ownership. Preserve focus, selection and password handling.
Source: [[file:../src/reception/ui/interactions.bl.org::  function update][update]].

** 21. P2 — Give controller islands an explicit lifecycle
The adapter compares controller-node JSON strings, reparses data and rebinds
controllers; some controllers use global IDs/selectors. Isolate each controller
to its root and make mount/update/dispose explicit. Share stable normalized
read data rather than embedding unnecessarily broad JSON in every frame.
Keep provider signup as a narrowly owned browser integration, not a generic
arbitrary-script extension point.
Sources: [[file:../src/reception/ui/interactions.bl.org][controller dispatch]],
[[file:../src/reception/ui/pms_interactions.bl.org][PMS adapter]],
[[file:../src/reception/ui/messaging_interactions.bl.org][messaging adapter]].

** 22. P2 — Consolidate the browser command envelope
Generic forms, PMS, profiles, messaging and signing each implement fetch,
pending state and feedback differently. Share transport/error/pending plumbing
while keeping typed domain commands and their original receipt rules. Model
attempt identity with its captured payload and outcome; do not silently replace
an uncertain request with a new ID. Uploads, secret rotation and OAuth still
need their explicit HTTP boundaries. Moving everything to socket intents is
not a prerequisite for efficient pages.
Sources: [[file:../src/reception/ui/interactions.bl.org][generic submission]],
[[file:../src/reception/ui/profiles.bl.org][profiles]],
[[file:../src/reception/ui/webhook_signing.bl][signing]].

** 23. P2 — Split web transport, read models and feature screens
=web.bl= combines identity, route tables, webhooks, commands, rendering, assets,
provider setup, application startup and cleanup. =screens.bl= combines unrelated
features. Keep a small =live.app= factory with per-feature screens; extract
HTTP handlers, session policy and assets. Read modules should consume immutable
values; UI modules should not import the command owner or provider contexts.
Split by responsibility rather than creating a wrapper for every function.
Sources: [[file:../src/reception/web.bl][web]],
[[file:../src/reception/ui/screens.bl][screens]].

** 24. P2 — Declare route capability metadata once
Routes appear in =page-paths=, multiple cases, production allowlists and special
SSR/socket authorization branches. Declare each feature's path, screen and
access requirements together and derive the appropriate adapters/allowlists.
Preserve actual HTTP403/404 behavior as well as socket refusal; an unavailable
component in a200 document is not automatically equivalent.
Sources: [[file:../src/reception/web.bl][route dispatch]],
[[file:../src/reception/production.bl][production routes]].

** 25. P2 — Make composition return explicit read capabilities
=application/open!= already owns acquisition/cleanup. Extend that boundary to
return a stable public read context and command capabilities. Optional workers
and transport startup should have named readiness stages. A disabled Meta or
agent flag does not currently mean all communication transport/execution
initialization is absent. Measure those stages before attributing cold startup
to Live, aliases or any individual import.
Sources: [[file:../src/reception/application.bl][application lifetime]],
[[file:../src/reception/communication.bl::(defn start!][communication startup]],
[[file:../src/reception/web.bl::(defn serve!][serve!]].

** 26. P3 — Isolate synthetic seed and development catalogue concerns
=web/serve!= selects the synthetic seed in non-live mode and sets a sibling
Librarium runtime path. The UI catalogue initializes an index from its render
path and uses process-local context. Keep development fixtures/catalogue in
their own composition and make resources explicit. Audit real require/loader
phases; a static dependency edge or an aliased require alone does not prove an
eager startup cost.
Sources: [[file:../src/reception/web.bl::(defn serve!][startup]],
[[file:../src/reception/seed.bl][seed]],
[[file:../src/reception/ui/catalog.bl][development catalogue]].

** 27. P3 — Reuse Loom presentation primitives behind Backdesk components
Backdesk has a33KB shared stylesheet plus separate theme tokens and repeated
buttons, badges, fields, dialogs, tables and empty states. Define its brand as
tokens, then adopt =loom.ui=/=loom.box=/=loom.parts= through small Backdesk
components while preserving the current appearance and accessibility. Adapt
procedure schema presentation to reusable fields; keep authoritative domain
validation in the existing procedures. This improves consistency and maintenance;
it is not a demonstrated cure for the four-minute startup.
Sources: [[file:../src/reception/ui/style.bl][styles]],
[[file:../src/reception/ui/parts.bl][parts]],
[[file:../src/reception/ui/forms.bl][forms]].

** 28. P3 — Separate cacheable assets from personalized documents
CSS is embedded in each full document, the combined adapter ships every
controller, and font routes read files directly. Use versioned static CSS/JS/font
assets with appropriate caching, retaining request-collected Loom rules for
dynamic styles. Keep personalized HTML and sensitive setup pages under their
appropriate cache policy. Check actual response headers before claiming a
browser asset-cache hit.
Sources: [[file:../src/reception/web.bl::(defn live-document][live document]],
[[file:../src/reception/web.bl::   (= path "/interaction.js")][assets]].

** 29. P2 — Remove duplicate read/transport paths after consumer inventory
SSR fallback branches and compatibility state/revision endpoints coexist with
the Live frame; the separate Python guest app also remains. Share actual read
models across required transports and delete only paths with verified retired
consumers. Current Live browser tests explicitly assert no revision/PMS/Meta
polling: do not reintroduce polling as a simplification.
Sources: [[file:../src/reception/web.bl][HTTP compatibility]],
[[file:../web/server.py][Python guest app]],
[[file:../tests/communication/live_frame_browser.py][Live transport checks]].

** 30. P1 — Make diagnostics and tests prove bounded work
Record worlds/screen/realize/diff/serialize/queue phases, actual Datom rows and
seeks, patch bytes and browser-applied route time. Current broad liveness and
functional tests do not establish a page budget. The desk growth test permits
linear whole-world growth; add fixed-page tests with more unrelated hotel and
foreign-property history, unchanged-render checks, duplicate-ID checks,
writer-held reads, temporal transitions and reconnect preservation. Repair the
stale lifecycle fake form before using that script as a release gate. Preserve
public error responses, but emit bounded internal diagnostics instead of
discarding every unexpected exception into unavailable/false/500.
Sources: [[file:../tests/runtime/desk_projection_test.bl][growth tests]],

* Implementation order and limits

1. Establish route/query/patch counters, fix the small harness, and retain an
   unchanged real seed/store baseline. Keep cold compile/load readiness separate.
2. Migrate Guests to bounded authorized query/pull, then conversation detail,
   then Today aggregates. Retain command and disclosure semantics throughout.
3. Remove rendering randomness, duplicate field IDs and missing stable keys;
   consolidate timestamp formatting and add route-specific deadlines.
4. Split the app factory, HTTP adapters, read models and screens. Consolidate
   drafts/controllers and adopt Loom presentation incrementally.
5. Only then consider narrower invalidation or additional materialized read
   projections, justified by measured fan-out. Never add arbitrary Live attribute
   filters or broadly bypass its ordinary subscription/authorization contract.

The audit identifies concrete work and bounded isolated evidence. It does not
assign a percentage of the current page/startup latency to any finding, claim
all queries are unindexed, claim successful full browser qualification, or
attribute Backdesk's code-analysis MCP timeout to its page renderers.
