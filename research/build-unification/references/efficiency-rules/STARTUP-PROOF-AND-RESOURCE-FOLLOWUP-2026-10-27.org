* E: broad production preload is a distinct startup cost

The actual assembled R17 launcher emitted:

Startup preload complete: 573 namespaces in 46392 ms
discovery-us: 8814054
loading-us: 37577833
reductions: 4042193192
#+end_example

These are scalar fields from
[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/actual-start-r17-diagnostic-r1/child-output.log][the actual child log]]. They describe SDK startup preload, not the separately
timed application installer, route read, browser mount or first usable frame.
The slowest namespace list contains UI, tooling, verification and solver modules;
it does not by itself prove that each can safely be omitted from this runtime.

[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/actual-start-r17-diagnostic-r1/actual-start.json][The launcher receipt]] failed at unsigned readiness with child exit 1 and a
store-already-open error. It recorded zero signed HTTP attempts. Consequently
this experiment proves neither successful deployment nor signed-request time.
The 46.392-second preload alone exceeds the existing 30-second packaged startup
target, but it is not the complete failure explanation: storage admission failed
as well. Do not add overlapping diagnostic phases into an invented total.

A SEPARATE private public-loader experiment selected 46 SDK roots and measured
23.924 seconds for their closure preload. Its full install measured 53.511
seconds, including all preload cost inside the install clock. All 350 project
native units and 1,270 member modules matched afterwards. This is
[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/all-sdk-public-loader-r17-diagnostic/phases.json][a different loading-order experiment]], not a 573-to-46 namespace reduction or
a qualified production startup improvement. A root count is not a transitive
loaded-namespace count.

P: a production application should receive an inspectable, compiler-owned
phase graph: definition dependencies, emitted runtime dependencies,
initialization effects, optional tooling and explicit serve activation. The
packager should report the dependency reason for every retained namespace and
the work due before readiness. A narrower startup graph must preserve macro
expansion, native declarations, provider registration, semantic generation and
runtime ownership; importing less based only on names is unsafe.

* E/S: exports, initialization and activation need separate contracts

The native artifact has several distinct boundaries: source namespace,
complete unit, forwarding exports, body exports/local functions, unit
initializer, loaded marking and source fallback. Profiling only a public
forwarder can miss the actual work. The retained
[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/native-guests-profile/body-exports.json][R17 body-MFA inventory]] identifies actual emitted body functions and local
callbacks; the private profile checks code identities rather than guessing
their names. Public export presence is not proof that initialization or
runtime ownership has completed.

Single-run private startup experiments retained all initialization calls/order,
verification-before-publication, 350 native units and 1,270 member MD5 checks:

| Variant | Install ms | Publish ms | Init/mark ms | Fallback ms |
|---------+------------+------------+--------------+-------------|
| Original baseline | 45151 | 4872 | 24115 | 12949 |
| Public loading session | 37500 | 4693 | 23468 | 6062 |
| Session + one eager bulk publication | 36297 | 4161 | 22610 | 6168 |

Receipts are [[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/r16-startup-phases/phases.json][baseline]],
[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/loading-session-r16-diagnostic/phases.json][session]] and
[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/bulk-session-r16-diagnostic/phases.json][bulk/session]]. Flattening the member list cost 3 ms in the last run. The
bulk change's 532 ms publication difference is modest, and initialization also
varied by 858 ms; these single cold samples do not establish a robust total
speedup attributable to bulk publication. No variant was promoted by this note.

S: public =BeamLisp.Loader/with_loading_session= and
=BeamLisp.Env/publish_binaries!= exist in this SDK. Using them does not grant
permission to bypass duplicate-module, schema, runtime-floor, code-lease or
retirement checks, mark code loaded early, or claim transactional publication
rollback. The experiment eagerly flattens verified members with finite loops;
it does not retain the complete BEAM vector in a lazy callback or wrap serve
in an indefinitely open loading session.

P: expose these phases and their dependencies in one native application
manifest, including body-MFA provenance and a readiness receipt. Distinguish
verified bytes, published code, initialized definitions, activated resources
and listening/signed-ready service states. Require separate negative tests
for missing members, stale code, failed initializer and partially acquired
resources. A unit-level purity or constructor pass cannot prove every phase
safe to defer or merge.

* E/S: 355 identical mark-map acquisitions are proof overhead

The actual closed-fixture R17 profile admitted the same full DTO/HTML and
witness, with all 350/1,270 native identities verified. Context capture took
about 33.2 ms in the zero-derived traced sample, of which the capture body was
about 29.3 ms. Follow-up attribution found a 355-attribute world-stamp path
repeatedly obtaining the entire merged attribute-mark map. Revision lookup was
roughly 1 ms; rebinding locals did not remove the underlying acquisition cost.
These are direct phase findings, not a claim that capture accounts for all
browser latency. See [[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/native-guests-profile-r1/zero/profile.json][the zero fixture profile]] and
[[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/native-guests-profile-r1/positive/profile.json][the positive fixture profile]].

S: [[file:/nix/store/xsnzdz8aggcxlng5q4gg26r88jq1asy9-source/priv/lib/datom/attr-basis.bl][datom.attr-basis/basis-t-for]] is exactly a lookup in the public =hydrate!=
result. That result merges durable evidence and live in-flight/build hints;
it is not merely a committed transaction snapshot. The current
[[file:/nix/store/xsnzdz8aggcxlng5q4gg26r88jq1asy9-source/priv/lib/datom/cache-validity.bl][datom.cache-validity/read-stamp]] calls it once per requested attribute.
Its result also includes query-definition generations and atomic evidence
that the attributes have no computed providers.

Missing attribute marks carry essential semantics. With explicit empty proof
enabled, a known attribute gets one raw AEVT prefix page of limit one. Only an
empty exhausted prefix proves absence. Retractions, historical or future facts
keep that prefix nonempty; unknown attributes use the exact reader basis.
Mark zero is present evidence. Future marks refuse. Copying only the integer
marks and dropping these branches would weaken the contract.

An initial exact-DB checkpoint-reuse idea was deliberately set aside. Public
=datom.conn/TX-COUNTER-KEY= is an allocated high-water mark, not a committed
head. In-flight =record-ops= can publish future marks before physical commit;
=note!= can publish a future build hint without advancing that counter at all.
Raw physical prefix writes can also bypass marks and the counter. Therefore
equal DB identity and equal head alone do not preserve the old absence proof.

P: the SDK owner should offer a bounded aggregate read-evidence operation
which performs one merged-mark acquisition, preserves the exact per-attribute
missing/empty/future rules, and returns ordered evidence with provider,
definition, schema, view and explicit coverage provenance. The owner can state
whether its result is a coherent native snapshot or a conservative sampled
proof; those are different promises. Expose actual prefix reads and budget
dimensions. Unknown/error/race must retain the existing refusal/fallback
semantics, not certify empty data.

The current PRIVATE SDK305 compatibility experiment instead takes two fresh
merged maps around the original rules and falls back to the original public
function on mismatch/unsupported/error. It retains every empty-prefix probe;
it caches no checkpoint. Deterministic negative fixtures cover raw writes,
future hints, computed shadows, filters, wrappers and between-map mutation.
The subsequently completed [[file:/home/othman/code/products/backdesk-booking/.local/deployable-execution-protocol/bulk-world-stamp-r18-r1/profile.json][actual R18 private probe]] exited natively with
status zero. Eleven negative controls, three between-map races (observer
executed exactly once), and two isolated provider controls passed. Fixture,
Source, resources and 350/1,270 native identities were unchanged. Recorded
median work was:

| Original lazy attribute selection | Eager selection, original SDK proof | Eager selection and private bulk proof |
|-----------------------------------+-------------------------------------+----------------------------------------|
| 22.572 ms / 2.428 million reductions | 10.132 ms / 1.010 million reductions | 7.705 ms / 0.731 million reductions |

The probe recorded 16 fast calls, eight original fallbacks and 2,024 raw-prefix
checks. Other authorized diagnostics overlapped this run, so absolute timings
are diagnostic. The larger measured opportunity was the finite eager
attribute-selection boundary; the additional bulk-kernel delta was about
2.4 ms and adds SDK-compatibility policy. The implementation recommendation is
therefore the minimal eager-selection change first, not automatic promotion
of the copied kernel. No browser or deployment gate follows from this probe.

The private helper is an experiment, not a new supported SDK API. Any eventual
application adapter also needs its own code
generation included in semantic evidence; the SDK's namespace list does not
automatically cover new application proof code.

* E/S: Fjall logical stop is not confirmed OS ownership release

The actual child launcher failed to open its synthetic hotel because another
OS process owned the Fjall directory. That typed admission failure is useful
protection against concurrent access; the failed attempt alone does not prove
which reference or shutdown phase retained the handle.

S: [[file:/nix/store/xsnzdz8aggcxlng5q4gg26r88jq1asy9-source/priv/lib/datom/store-fjall.bl][store-fjall]] documents a directory-inode OS lock held by the native resource's
file descriptor. Its =Closeable/-close= syncs; it does not itself explicitly
destroy every extant native resource reference. SDK
[[file:/nix/store/xsnzdz8aggcxlng5q4gg26r88jq1asy9-source/priv/lib/datom/conn.bl][connection close/release]] removes registry ownership and drains the writer;
caller-held database values can still retain handles. Collection or OS process
death releases the last native reference/descriptor. Thus actor stop, writer
drain, durable sync, registry retirement, last-handle release and cross-process
reopen readiness are separate observations.

P: lifecycle APIs should return explicit completion evidence for the promised
resource boundary. If immutable read views intentionally outlive a connection,
their ownership/lease is part of that boundary; silently invalidating them to
force close would change semantics. Provide an owned scoped-open pattern with
documented escape rules, and distinguish graceful shutdown from confirmed
cross-process handoff. Qualify this with a fresh child process actually opening
the canonical path, plus retained-view, alias, error-path and process-death
cases. An SMT ownership model over =close= calls cannot establish native fd
release without a qualified native adapter contract and real replay tests.

For the present no-SDK-change product plan, keep fixtures in an owned seeding
process that exits before the consumer, close/drain all named journals and
owners, and verify actual reopen. Do not delete lock files, weaken ownership
checks, or treat a successful logical stop as a completed handoff.

* Consequences for the parallel implementation and research tracks

1. Keep product changes on current public APIs and existing native fences.
   Private loader/proof experiments need parity, provenance and negative tests
   before promotion; proposed upstream APIs are not product dependencies.
2. Measure SDK discovery/load, application install, resource activation,
   listener readiness, first signed response, SSR, socket mount, post-return
   deadline work and warm browser interaction separately. Preserve the
   original 30 s startup, 2 s usable, 500 ms warm and 100 ms local targets.
3. Prefer aggregate proof acquisition owned by Datom over an application
   checkpoint cache with an incomplete head/absence model. Preserve may-refuse
   validation even when its rendered result appears unused.
4. Evolve publication/type/effect/ownership tooling around phase and resource
   contracts, current identities and explicit unknowns. Solver success over a
   logical model must remain separate from native code/resource conformance.
5. Require evidence for exact emitted bodies and actual native release runs.
   Existing source-browser and phase improvements do not erase remaining
   startup/initial-frame/Guests latency failures.
