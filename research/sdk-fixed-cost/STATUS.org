#+title: SDK and unchanged application fixed costs

* Starting point

The previously qualified producer work was merged into main at e5d1defa6.
This round continues on perf/producer-latency from that merge. Main has since
advanced independently; these measurements use the frozen merge, not its ongoing
Datom changes.

All production measurements run in a private checkout on the Source-described
Build backend (ssh-ng://beam-build-station), using ordinary checkout preparation.
Build had 19 GiB available and no BEAM VMs before profiling. Services have finite
runtime, 4–8 GiB memory caps and zero swap; SDK/application guests retain their
recipe caps. Commands and builds run serially. One shell quoting mistake started
a local preparation client; it was stopped before proceeding. Local source was
unchanged, and its owned processes are gone.

* Baseline

commands-before.json records the actual public command timings and reuse checks.
Cold command median: 5.224 s. Warm command median: 0.265 s. First application
build: 36.691 s; unchanged: 2.870 s; one-file edit: 34.137 s; fresh-process
unchanged: 10.686 s. The edited product compiled one unit and restored one; the
unchanged provider's six files remained identical. Warm VM peak RSS: 434 MiB,
swap: zero. Client RSS in this receipt does not include Nix daemon workers.

application-profile.json captures real dispatches through the immutable SDK,
with build helpers preloaded: warm builds take 2.654/2.673 s; application
selection alone takes 2.200/2.223 s. Full inventory verification is retained.
The first instrumented dispatch is 4.491 s and includes cold helper work.

sdk-profile.json contains exclusive Erlang call-time results from actual SDK
production, with 0 units compiled and all 532 restored. Library production:
19.850 s; image assembly: 41.874 s; archive packing: 16.458 s. Call-time tracing
does not account for all image work, so a separate stack sampler follows before
choosing an image optimization. Instrumented timings are diagnostic, not claimed
speedups.

* Experiments

application-sharing.json compares three alternating strict evaluations using
one pinned package set across source snapshot, selector and recursive unchanged
application construction. Median evaluation falls from 2.411 to 2.249 s (6.7%).
Every source, output and derivation identity is exactly equal. This small cut
does not eliminate the dominant full worker derivation evaluation.

Probe generators are retained here. They alter only private profile drivers or
private recipe copies. Paths in probes identify this round's exact immutable
SDK and platform. make-sdk-profile.py and make-sdk-sampler.py consume an original
produce-sdk.bl copy in .local/fixed-cost/produce-sdk.original; SDK production
then uses the normal Source backend. Restore the driver and select the original
SDK after profiling.

native-sharing.json compares three alternating evaluations of the same eight
native sources. Median wall time falls from 15.517 to 3.164 s; evaluator peak
RSS falls from 1339 to 392 MiB. All eight derivation and output paths remain
exactly equal in all six runs. The first probe incorrectly used an archive
without an untracked .cargo directory; that read-only evaluation refused a
missing source object. The corrected probe gives both recipes the same explicit
source root, and its measurements alone appear in this receipt.

The implementation supplies the same pinned package set to native products,
desktop checkout products and application native declarations. SDK construction
also passes its existing native product set to its checkout platform instead of
constructing it again. Application selection shares packages with its snapshot
and unchanged-request recursion. This is evaluation-local sharing: no persistent
validation, source, derivation or authorization cache is introduced.

application-identity.json qualifies the final selector with the actual immutable
SDK/product: separate and combined recipes select the exact same source/output/
derivation. Force requests return no cached product; edited sources select a new
unrealized snapshot; symlinks refuse. The trusted recursive constructor remains.

sdk-samples.json records 5727 sampling iterations from actual SDK production.
The two hottest running stacks are LazySeq.force_state (775 observations) and
LazySeq.new (399), inside the final build-image digest-index fold. These are
stack counts, not a complete phase-time attribution: tail calls and waiting
workers affect which stacks retain their caller. The index currently makes
lazy sequences per unit while capturing the entire verified module map.
The candidate uses strict Enum folds for this already-eager publication step;
every proof and final metadata boundary remains intact. image-equivalence.json
compares the frozen immutable SDK producer with the candidate Source under a
private namespace in one capped VM. All 532 units restore; assembly takes
42.455 s before and 4.876 s after (88.5% lower). All 2053 published files are
byte-identical, including the 2051 BEAMs, SDK inventory and precompiled index.
The process peaks at 916 MiB RSS, zero swap; the whole capped tree's observed
peak is 1657 MiB. This is a matched assembly control, not full production wall
time. Final production qualification is pending.

The sampler's first attempt failed Elixir compilation before production; its
driver was restored and it contributes no timing. The corrected generator has
a lightweight Elixir preflight, and the successful run restored the original
SDK selection afterward. Streaming worker logs can contain an interrupted
JSON line; sdk-samples.json uses the complete exit-trap replay.
