#+title: Fresh compiler preparation — bounded reader evidence

* Implementation and correctness boundary

The production change shares successful immutable reader output between the
constructor and Loader metadata paths inside an actual private artifact
constructor and its existing Source snapshot. No prepared artifact is reused.
Keys include exact Source bytes and attribution, target compiler key,
authenticated kernel world, native publication epoch and the loaded identities
of Reader/facade/body/AtomGuard/AOT. Publication and code identities are checked
again after parsing or replay. An active or changed publication cannot provide
reusable evidence. Source selection/currentness, input receipts, preflight,
macro fuel, ownership, emission and verification remain independent.

Guard resets and tagged accounting tokens replay in order under current atom
limits and with the original host/bare exception mapping. Failed parses are
never cached. Missing/mixed recording ABI falls back to direct reading. A
recording is bounded to 262144 events; retention to 512 entries/64 MiB encoded
data. The existing Source pass finally block restores or deletes the cache.
This byte bound describes encoded data, not a 64 MiB process RSS guarantee.

Production Source is frozen at ed58c5e7c. Later commits add tests and evidence.
The native Source-described Build backend produced this compiler and passed its
P/B/C equivalence proof for all 141 files; compiler-proof.json retains the keys
and manifest/qualification digests. Machine placement, scheduler settings and
memory caps stay outside the language implementation.

* Performance gate

The repeated pilot uses six actual SDK namespaces against the complete SDK
catalog: errors, proc.queue, reload.generation, datom.conn, bl.cli and build.
Every unit gets a fresh workspace, preparation, emission and verification. The
batch shares only the existing Source snapshot. Three alternating fresh-process
pairs emit 29 byte-identical files in every control. reader-pilot-paired.json
retains every observation, CPU time, load and /proc memory sample.

The SDK producer saves 428 seconds (7.1 minutes). This is one full paired run
on a shared station, not a dedicated-host confidence interval. The packing
variation is not attributed to this patch. The repeated pilot provides an
independent smaller performance gate. Native worker phase wall time excludes
outer Source capture, coordinator preparation and Nix evaluation; those are
not speedup claims here. Full-worker compiler-child RSS was not collected.

native-sdk-result.json retains every unit preparation time, phase, artifact
selection, inventory digest and compiler identity. worker-profile.py evaluates
private copies of unchanged production helpers, disabling only the optional
reader cache in the control. A sparse prepare_unit call/return trace collects
wall times without tracing reader hot paths. native-report.py requires the
complete target inventory to match; only the diagnostic retained producer
subtree is excluded. These diagnostic SDKs are not release inputs.

The ordinary unmodified driver is restored for qualification. Its first normal
production restores all 534 units, compiles none, verifies every restored unit
and retains all 3228 references: unit-store work takes 8.28 seconds. Remaining
fresh-unit costs include constructor interpretation/traversal and emission;
remaining fixed work includes compiler-floor qualification, process startup,
coordinator/Nix setup and image assembly. Hashing/copying were a few seconds
in the fresh controls and are not the principal fresh-build bottleneck.

* Qualification and remaining gates

Focused native controls cover guard replay/refusals, bytes/attribution and
publication invalidation, failed-parse exclusion, bounds and cleanup, followed
by the affected constructor/ownership/budget/reader tests. Application controls
exercise fresh processes, warm repeats, unchanged products, a one-file edit,
provider byte equivalence and a source-free receiver with integrity refusals.
SDK controls require unchanged selection identity and byte-identical restored
units after a unique one-file Source edit. These execution checks are pending.

Consumer discovery currently verifies all 16 mapped boundaries and 9 external
writers; all 9 focused selection/receipt tests pass. This is inventory evidence,
not executed release qualification. Full release CI and shard balance remain
separate release gates; no fixture or coverage has been removed.

Heavy work runs serially on the configured Build station, inspected before
startup (20.7 GiB available, 29 MiB global swap, no BL VMs). Controllers are capped
at 4–8 GiB with no swap; SDK leaf workers retain the repository's existing VM
resource limits. Shared station load varies significantly. Pilot RSS is measured
inside the compiler VM; full-worker compiler-child peak RSS is not measured by
the outer client/controller and must not be inferred from its much smaller RSS.
Private command realms are stopped in cleanup; independent Source workers exit
at the end of their jobs.

* Rejected experiments (not in production)

** Declaration discovery

The six-namespace diagnostic observed 91 Loader.read_forms calls in addition
to 106 Reader.read_string calls. Loader declaration discovery reparses Source
that constructor_unit! has already parsed. Seed its existing context-local
declaration map using those exact reader forms and the Loader's unchanged
fold. There is no new cache or cross-workspace lifetime. Existing prior
declaration entries, Source selection/digest/currentness checks, compiler and
kernel ownership, budgets, prelinking and emission remain in place.

Baseline production compiler Source is unchanged since 24ce4455d for AOT and
Loader. This development branch starts at 0f81a7be9; unrelated main work is not
changed. Heavy work uses the Source-described Build station, inspected before
startup (20.7 GiB available, 29 MiB global swap, zero BEAM VMs), serial controllers
capped at 4 GiB/no swap. Machine placement and scheduler settings stay outside
language code.

** Controls

probe.bl calls actual open_workspace / prepare_unit / emit_unit / verify_unit
against the complete unchanged catalog in the retained SDK. Each unit gets a
fresh workspace; the batch uses the same with_source_snapshot boundary as
normal unit production. Units: errors, proc.queue, reload.generation,
datom.conn, bl.cli and build. All are prepared afresh; no prepared unit or
compiled target is restored. datom.conn is the largest SDK Source unit.

compile-pilot.bl emits the two actual candidate host modules with load? false.
A development VM boots the original SDK, then loads these modules explicitly.
This is a controlled performance/component experiment, not a qualified SDK,
compiler floor, native admission claim or substitute for Source production.
The original SDK and floor remain immutable. Full production proof is required
before merging runtime changes.

The traced diagnostic observed 40.903 -> 27.359 seconds preparation and
91 -> 7 Loader reparses; all 29 emitted files match byte-for-byte. Emission
also varied, so this single instrumented timing is not proof of a speedup.
Three untraced alternating fresh-process pairs rejected this cut. With both
variants compiled through identical host emission/options/attribution,
preparation medians were 23.480 / 23.906 s, and whole cold commands 40.998 /
41.953 s. All 29 files match. No full compiler build or broad qualification
was launched. rejected-declaration-reuse.json and .patch retain the evidence;
production files have been restored. The initial seed-versus-development
compiler controls are excluded because their generation methods differed.

Exact call_time tracing of frequent lookups substantially inflated preparation
wall time. Further attribution uses a bounded sampler active only during
preparation, and all performance gates continue to use untraced fresh commands.

** Native raw traversal

The preparation-only sampler observes Reader work and bounded interpreter work,
including the internal raw cost walk. Replacing pending task allocation with
native recursive traversal preserves tuple/map visit order, costs, depth checks,
walk fuel and existing container/recipe validation. Differential controls across
2452 cases produced identical results, refusals and remaining fuel (SHA256
dd9e80d04db5295a8bd8404b959d13be4624eb383dd4d314b9ea04c40cc27ac8).

Matched untraced preparation medians: 24.343 -> 22.495 s (-7.6%). Whole cold
commands: 41.950 -> 40.296 s (-3.9%). Two pairs improve and one regresses; this
is insufficient to justify full production qualification yet. All 29 emitted
files match. walk-only-paired.json preserves every observation.
