#+TITLE: Env-owned adoption and warm compiled entry

* Acceptance belongs to the receiver

The old image adoption path inserted an Env-owned physical lease from the
requesting process, then asked Env to store its private proof. A caller death
could split those steps. The capacity-fence control observes the old requester
performing lease commitment; an owner lifetime in a tuple did not move execution
of the commitment into that owner.

Publication still captures/hashes/loads actual code outside registry turns.
After releasing the caller's publication fences, the fixed acceptance command
uses the existing nonblocking custody-fence protocol inside actual Env. It must
acquire the complete module and capacity set, recheck current loaded MD5s, then
insert the lease and private proof together. A failed proof insertion removes
that exact lease. Contention returns without mutation; the requester retries
outside the owner turn. This avoids making Env wait for a caller that itself
needs an Env reply. The turn receives bounded fingerprints/IDs, not BEAM bytes.

Once the real request is queued in Env, requester death can no longer strand a
half-committed image. Env completes its own metadata work or refuses before
commitment. This does not execute a user callback or an initializer in custody.

* Private initialization state

The state is =absent -> adopted -> ready=. Adoption records an uninitialized
image. Rt/Core initialize outside registry turns under the existing namespace
lock. Completion checks the actual Env PID that began initialization. A dead
requester leaves =adopted=; another requester retries the pure kernel setup.
A replacement Env starts =absent= and refuses completion from the old epoch.

The old public =:bl_runtime_initialized= row no longer selects readiness. It is
ordinary metadata and cannot stand in for the private owner state. The full
compiler's separate seeded flag remains false in compiled-only execution.

Warm requests reuse the adopted image. Program unit bytes still validate at
each entry, and the native Loader still checks the retained support code's
current MD5s. Floor capture, disassembly and hashing run only for a new Env
image, rather than once per program request. This is not a zero-I/O or
constant-time activation claim.

* Native controls

The adoption process publishes genuine captured support bytes, then uses the
existing capacity fence to verify requester-side contention and owner
responsiveness. Killing that unaccepted requester must leave no image lease.
It next suspends actual Env, queues the real fixed acceptance command, observes
the real mailbox request and kills its requester before resuming Env. Lease and
proof must complete exactly once, without a caller continuation.

The captured queued request is size-checked. A public readiness lookalike must
not skip Core setup. Another requester is killed while initialization waits at
the actual global publication fence; readiness must remain adopted and retry
must succeed. An old Env PID cannot complete a replacement epoch.
