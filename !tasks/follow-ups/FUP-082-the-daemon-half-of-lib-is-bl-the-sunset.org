* The question, and what PLAN-116 got wrong

PLAN-116's D6 said *"what stays Elixir forever — the daemon (tree identity, tokens, protocol),
launcher, native glue, and read-model shims. Anything that decides moves."* That list conflates
three different things, and only one of them is irreducible:

| # | category | can it run before bl exists in the VM? | verdict |
|---|----------|----------------------------------------|---------|
| T1 | the language's own bootstrap: reader, compiler, AOT cache, loader, `RT`, `Env`, the runtime types the compiler LOWERS ONTO | yes — it is what makes bl exist | irreducible until self-hosting (a separate, much larger project) |
| T2 | the program `bl` runs: `lib/beam_lisp/daemon/` — tree identity, paths, the socket protocol, the registry, names, the gateway, the CA, the HTTP reader, the executor, the workers | **no** — every one of these needs only sockets, processes, timers, filesystem and a place to be started from, all of which bl now has | **policy in the wrong language, with a sunset** |
| T3 | native artifacts: `native.ex`/`native_task.ex`/`z3_port.ex`, `cargo.ex` (NIF/port plumbing) | n/a — C/Rust, not Elixir policy | the artifact stays; its Elixir-facing shim is a name bl can call |

The discriminating question is not "is it a primitive?" (every daemon module can be called one) but
**"does it have to exist before the first line of bl runs?"** Nothing in T2 does. `Ports` is a file
format and a claim protocol. `Names` is string arithmetic. The daemon's `Server` is `gen_tcp.listen`
plus a framed protocol. The gateway is socket → socket. The CA is `x509` over `:public_key`.

The counter-argument is not "it is impossible", it is **"it is not free"**: the daemon half is the
crash-restart surface, and a bl namespace has no OTP-grade supervisor today. PLAN-116's prototype
answered that with `super/defsupervisor` + `reg/defregistry` (it really does build a supervisor tree,
with the child spec being `(start-link <defserver> <args>)`) — mitigated, not eliminated. So this is
a *scheduled* move with exit criteria, not an aspiration.

* What stays Elixir, and why that is an answer rather than a dodge

A language cannot be built by itself before it exists. `RT` (2,928), `Env` (1,374), `Aot` (973),
`AotCache` (821), `Loader` (742), `Reader`/`Compiler`/`Emit`, `CompilerData`, `AtomGuard`,
`FormMeta`, and the runtime types the compiler LOWERS ONTO — `Vector`, `Sorted`, `Record`, `Refs`,
`Set`, `Num`, `LazySeq`, `Multi`, `Decimal` — are the machine, not the program. The measured
contract (grep of `priv/boot/*.bl` + `priv/lib/system/*.bl`): the compiler emits or calls
`BeamLisp.Env` (37×), `RT` (24×), `CompilerData` (22×), `Reader` (10×), `Vector` (9×),
`AtomGuard` (9×), `ExInfo` (7×), `Record` (6×), `FormMeta` (6×), `Refs` (5×), `Num` (5×),
`Loader` (5×), `Set` (4×), `Link` (4×), `LazySeq` (4×), `Multi` (3×).

That tier is not a privilege, it is a *contract* — and this FUP's job includes keeping it from
growing: **a module in T1 is a module bl cannot express yet, and every new name in it must be
justified as such.**

* The sunset, in stages — each with an exit criterion

- **S0 (in force now)** — no new policy in Elixir. A new capability lands in `priv/std/bl/*.bl.md`
  first; if it cannot, the plan that added it says why. (PLAN-116's rule, kept and sharpened.)
- **S1 — identity**: `paths.ex` + `names.ex` become `priv/std/bl/{paths,names}.bl.md`. *Exit:* a bl
  program computes its own tree id, runtime dir, socket/token paths and host names, and the daemon
  takes those paths from the same computation (no second implementation).
- **S2 — the registry**: `ports.ex` becomes bl, including PLAN-117's broker (a listener handed over
  instead of a number reserved). *Exit:* `bl ports` and `bl gateway` read a registry whose writer is
  bl; the Elixir module is deleted, not wrapped.
- **S3 — the session itself**: `daemon.ex` + `server.ex` + `listener.ex` + `protocol.ex` — the warm
  session is a bl program. *Precondition (the pass-the-parcel):* a bl program can BE the daemon, i.e.
  `bin/bl` → bootstrap → `priv/std/bl/daemon.bl.md` (PLAN-116's S4 "detached boot of a std
  namespace", still unproven). *Exit:* `bl daemon start/stop/status` runs a namespace; the handshake
  and token path are PORTED (not rewritten); crash-restart is demonstrated by killing the namespace
  and showing the session comes back with a sentence naming what died.
- **S4 — the services**: `workers`, `watch_registry`, `index_worker`, `io`/`std_err`, `executor`,
  `inspect`, `http`. *Exit:* a session with no Elixir process in its supervision tree; the MCP/HTTP
  surface and the Watch bus served from bl.
- **S5 — the gateway and the CA** (PLAN-116/117). *Exit:* `gateway.ex` and `ca.ex` deleted, the
  read-model shims point at what the bl side publishes, the two PLAN-105 behaviour fixes kept.
- **S6 — the end state**: `lib/beam_lisp/daemon/` does not exist. What remains is T1 (+ T3's shims),
  and this FUP closes with a *gate*, not a note: a test that fails when a `.ex` appears under `lib/`
  outside an explicit allow-list (the allow-list being exactly the bootstrap modules), so the
  boundary cannot erode silently.

* The order changed: the gateway is the wedge, and PLAN-117's branch carries it

PLAN-117 puts the name gateway in bl. That is not a detour from this FUP — it is the first stage of it,
and a better first stage than this FUP originally listed, for three reasons:

1. The gateway needs none of the hard parts of the session daemon: no sandbox, no tokens, no per-tree
   protocol, no request queue. It is sockets, a listener, a route table and a CA — so it proves "a bl
   program can be a long-lived, supervised, detached OS process" while the failure, if it comes, is
   unambiguous about which of those it came from.
2. It BUILDS the three things S3 was blocked on, instead of spiking them: (a) a detached boot from the
   same place `bin/bl` boots from; (b) hot reload through the reload machinery with state kept; (c) a
   crash that restarts and leaves a sentence naming what died.
3. S1 and S2 here (`paths`, `names`, `ports`) are LITERALLY PLAN-117's I1/I2. Doing them twice — once
   so the gateway can cut over, again so the daemon can — would be two implementations of one need,
   which the repo rule forbids.

So the order becomes:

| order | what | was |
|-------|------|-----|
| 1 | PLAN-117 I1-I4: the registry, the derived path, the CA in bl, the gateway in bl | the *end* of this FUP (S5) |
| 2 | S1/S2 finish: `paths`/`names`/`ports` have no Elixir owner left | start |
| 3 | S3/S4: the session daemon and its services, on the same branch | middle |
| 4 | S6's gate: no `.ex` outside the bootstrap allow-list | end |

** Guardrail — the branch is a stream, not a big-bang.** `main` moved 13 commits in one session while
PLAN-117 was being designed. So each I-step merges to `main` at its gate, and each stage here does too;
the branch merges `main` in before starting the next one. A branch holding "the names work AND the
session daemon AND the language cutover" unmerged for weeks cannot be verified at all — and the thing
it would break (the daemon every `bl` command talks to) is the tool you would use to fix it.

** What the reload machinery gives a daemon, and what it does not** (measured against
`priv/std/reload/ward.bl`'s own four properties — ward is a TEST runner, and a daemon is not: it wants
long-lived state where ward wants none).

| ward's property | usable by a live daemon? | why |
|-----------------|--------------------------|-----|
| ISOLATION — each unit in `env/isolated`, destroyed on the way out | **no, not directly** | a daemon's whole point is long-lived state (listeners, the CA, the route table). The unit of replacement is a NAMESPACE, not a fork |
| COHERENCE-GATE — a static pass before a unit runs; a broken one yields a report instead of a crash | **yes, and this is the important one** | a live service must never adopt a half-edited namespace; the same pass that guards a live reload guards a live gateway |
| ALWAYS-LATEST — source read fresh, no beam in the loop | **yes** | an edit to `gateway.bl.md` needs no build step, so BUG-048's class (`beam ≠ source`) cannot bite the gateway |
| WARM — one warm base env, forks off it | **yes** | the prelude stays warm; only the changed namespace is re-evaluated |

What NONE of them give, and what S3's exit criteria must therefore test:

- **supervision** — a replaced or crashed namespace must restart, and the log must name it (PLAN-116's
  `super/defsupervisor` prototype is the mechanism; the detached boot is the missing half);
- **state migration across a replacement** — a gateway holds a listener and a CA, so "which of these
  survives a reload" must be explicit (`reload/migrate` and `reload/upgrade` are the nearest thing, and
  they are about a live image, not about one long-lived service's own state).

PLAN-117's K10 is this FUP's real gate on the mechanism: hot-reload a RUNNING gateway, with a broken
edit rejected and a good one accepted, and the listener, the CA and the route table still there.

**MEASURED 2026-09-17** (`!tasks/evidence/PLAN-117-prototype/k10.bl`, one OS process throughout, a
listener the harness owned, a namespace edited on disk under it):

- an edit is picked up **live, with no restart and no build step** (`reload/stage` + `reload/commit`,
  source read fresh) — `greeting` changed from `v1` to `v2-EDITED-LIVE` while the pid never changed;
- a **broken** edit is **HELD**, with a named reason — `{:kind :dangling, :msg "undefined var:
  svc/no-such-helper — nothing in the bundle or image defines it"}` — and the old code kept serving;
- and the one that turns into a design requirement: **namespace state does NOT survive a reload**
  (`hits` 2 → 0). A reload is a WHOLE-NAMESPACE replacement, so everything a daemon must keep across an
  edit has to live outside the reloaded namespace — a separate process, ETS, or a registry — and the
  reload must say which of those it kept. The gateway's listener, its CA and its route table are
  therefore NOT "state in the gateway namespace": they are services the namespace's code drives.

That last point is the reason the port is not merely mechanical, and it is now a number instead of a
worry. Supervision — a crashed or replaced namespace restarting under something that names what died —
remains unmeasured, and is S3's own exit criterion.

** "Checkpoints" — settled 2026-09-17.** The word appears nowhere in this tree (the only matches are
incidental bytes in `priv/embed/potion-code-16M-v2/tokenizer.json` and the `z3` binary), so it was
asked about rather than assumed. It means the three things that DO exist and are named in the table
above: the content-addressed analysis store (`bl cache`, `priv/std/bl/cache.bl`), the warm base env, and
the coherence-gated reload. **No new subsystem is implied**, so this FUP rides on those three — and the
one property they do not give (isolation) is the one a daemon does not want.

* What "done" means (machine-checkable)

1. `lib/beam_lisp/daemon/` is gone; `rg -l 'BeamLisp\.Daemon' lib/` returns nothing.
2. `bin/bl` starts the daemon as a bl program; `bl daemon status` works with no Elixir daemon module
   on the code path.
3. The corpus passes (`bl test`), the CLI verbs are unchanged, `bl doctor` reports no missing module.
4. The allow-list gate is in place and green.
5. The ported-not-rewritten list is honoured and tested: the token/handshake path, the sandbox
   handoff, stdio forwarding, and PLAN-105's two fixes (absolute-form normalization,
   one-request-per-proxied-route).

* Risks

- **Crash loops with no OTP supervisor above them.** Mitigation is PLAN-116's: the namespace is owned
  by the drop/daemon supervisor, the accept loop's death is visible in the log the verb reads, and
  the failure sentence names the namespace that died. Demonstrated at S3, or S3 does not close.
- **Hot reload / dev ergonomics.** The daemon's reload semantics (which module version a live session
  serves) must be preserved or explicitly re-decided. A bl daemon that cannot be hot-patched is a
  regression the user feels immediately.
- **The security surface must be ported, not rewritten**: hello/token, the peer check (same uid,
  socket perms), the sandbox boundary. A rewrite under time pressure there is how a local privilege
  hole opens.
- **Two implementations during the move.** Every stage is a cutover (one need, one implementation):
  the bl version replaces the Elixir one in the same change, never beside it.
- **Stopping after S5**, leaving identity/protocol in Elixir because "it works". S6's gate exists to
  make that visible.

* Non-goals

- self-hosting the compiler/reader (T1) — a different project with a different cost curve. Criterion
  for revisiting: bl gains a compiler written in bl that can build the tree's own image;
- rewriting the native NIFs (T3) in anything;
- any general "bl as a systems language" claim. This claim is narrow: **the program is bl.**
